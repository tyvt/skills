## 一、结论先行

1. **codex/gpt 系整体有效分 0.769–0.779，JSON 极干净（0–3 fmt），但工具选择是硬短板（M1 仅 0.51–0.67）。** 明显弱于 workbuddy/kimi-k3.1-pro（0.849）。
2. **共性画像：「会想不会挑工具」**——理解依赖链、路由、评审、判读强；但工具选择差，突出表现为 ①纯代码片段生成爱直接答、不肯落 code_editor；②爱加冗余前置 pwsh 步骤（先读再改/先读再看图），步骤多、efficiency 掉。
3. **不建议做主控 planner 首选**（M1 工具选择是主控核心能力，它们垫底）；**适合按题型做分工**（见第四节）。
4. **计费模型**（per-token），4 个有效分都在 0.77 左右，性价比不如 workbuddy/kimi-k3.1-pro；进池需按「质量×成本」权衡。

## 五、M1 工具选择根因诊断（原始输出核查）

共性错误模式（4 模型几乎一致）：
- **M1-4（纯片段代码生成）**：4 个全判 `direct_answer` + steps=[]，本应 execute_tools/code_editor → **倾向直接答、不落工具**。
- **M1-5（修测试）/ M1-6（看截图）**：爱加多余前置 pwsh（先读文件再改/先 pwsh 再看图），tool 命中占比与 efficiency 双降。
- **M1-2（粘贴日志摘要）**：部分判 direct_answer 不走 file_reader。

→ 若要复用 codex，需在 PLANNER_SYSTEM 强化「有落盘/看图/验证意图必须选对应工具，禁止直接答」的约束。

## 六、口径与局限

- 单轮计划产出评测，非端到端真实执行；M9 只测"是否规划用图像通道"，非真看图。
- codex 为计费模型，本记录不含绝对成本（按 token 计费需另算），仅作质量侧结论。
- 若要进编排器池，建议对 gpt-6-luna（规划/对抗）先做影子对照再定。
