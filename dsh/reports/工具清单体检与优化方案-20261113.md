# DSH 默认工具清单体检与优化方案

> 日期：2026-11-13 ｜ 对象：web profile / `standard` preset 每步固定下发给模型的工具目录
> 结论：清单整体已被历次 token 审计优化过，但**还剩一个最大的结构性漏点——OpenViking MCP 的 24 个工具绕过 gateway 直连常驻**。这是本方案的主攻项。

## 0. 体检对象与证据来源
- 权威配置：`~/.dsh/profiles/web/cordis.patch.yml`（1040 行）+ `--dump-config` 合成树。
- 实际下发清单：本会话模型侧工具目录（ground truth）。
- 度量：各 `dsh-tool-*` bundle 的 description 字符串字符数（≈4 字符/字）。

## 1. 现状盘点（工具从哪来）

`standard` preset 的实际模型侧工具目录，按来源分 8 组，共约 **67 个工具**：

## 2. 量化成本（每步重发）

工具 catalog 属于 **prefix 区，每步都随请求重发**（除非命中 cache）。按 bundle 内 `description` 字符串实测：

| 组 | description 字符数 | ≈tokens |
|----|------|------|
| agent-team | 2341 | ~585 |
| session-query | 1703 | ~426 |
| ask-user | 1518 | ~380 |
| fs | 1328 | ~332 |
| schedule | 923 | ~231 |
| workflow | 867 | ~217 |
| pwsh | 678 | ~170 |
| goal | 658 | ~165 |
| jobs | 637 | ~159 |
| fs-search | 590 | ~148 |
| present | 452 | ~113 |
| working-directory | 264 | ~66 |
| tool-web | 200 | ~50 |
| skill | 191 | ~48 |
| todo | 156 | ~39 |
| **小计（14 个 host bundle）** | **12506** | **~3126** |

> 注：上表只统计 `description`，未含 JSON Schema 的 `parameters`（属性名、类型、required、enum）与每参数描述。经验上 schema 体量通常是描述的 2–4 倍，故 **host 工具实际每步约 9k–13k tokens**。

**OpenViking 24 个工具**：其 schema 由外部 MCP 服务端（`127.0.0.1:1933`）运行时生成。**已实测（见 §7）：24 工具 JSON schema 合计 33,790 bytes ≈ 8.4k–9.7k tokens，占整个 toolsTokens(16,327) 的约 52%。** 每步常驻。

> 修正：§2 初稿对 openviking 体量按同类估 1.5k–2.5k 偏低；§7 实测后为 **≈8.4k tokens**，是工具目录里最大的一块。

**本会话上下文里已能观察到实物**：系统直接注入了 24 个 `mcp__openviking__*` 工具 + 1 个 `mcp__magpie-vision__*` 工具，全部逐条展开。这正是 mcp-gateway 当初为 dbx/context-mode 消除的「36 个工具 / 每步 13k token 固定重发」问题的**同款复现**——只是换成了 openviking。

## 3. 问题清单（P0/P1/P2）

### P0 — OpenViking 24 个工具直连常驻，绕过 gateway
- **证据**：`mcp.mjs` 的 `mountOpenVikingMcp` 直接 `ctx.plugin(mcpClient, buildMcpConfig(config))`，把整个 MCP 工具面挂进目录；本会话可见 24 个 `mcp__openviking__*` 工具。
- **对比**：dbx/context-mode 已改为经 `dsh-mcp-gateway` 单入口（`mcp_gateway` 一个工具，≈826 字符）。openviking 没有被一起收编。
- **影响**：每步约 1.5k–2.5k tokens 固定重发，且 24 个工具里日常真正用到的只是 `search/read/remember/tree/list` 少数几个；大量 `privacy_*`、`acl`、`list_users`、`cancel_watch`、`download` 属低频维护类，长会话里几乎不调用。

### P1 — agent-team（9）+ session-query（5）合成平台型大块
- 这两组对「多 agent / 跨会话回忆」场景必要，但对普通单线程编码任务是纯开销（14 个工具 ≈1k tokens/步）。
- `team_task_*` 4 个、`session_event_*` 3 个是细分工具，可考虑按场景收窄。

### P2 — 每类工具的小项冗余与可合并点
- `schedule_*` 4 个、`job_*` 3 个、`goal_*` 3 个：低频但数量散，可评估合并/延后加载。
- 同一会话不改工具清单是缓存友好的前提（token-policy 明确），**任何删减必须一次性做在新会话**，否则打穿 prefix cache。
- `magpie-vision` 只有 1 个 `analyze_image`，体量小、不建议动。

## 4. 优化方案（分级）

### 方案 A（P0，推荐，收益最大）：把 OpenViking 也纳入 mcp-gateway
给 `dsh-mcp-gateway` 增加一个 `openviking` server（或用「只暴露子集工具」配置），让 openviking 的工具也走「一个 `mcp_gateway` 入口 + 按需 list 后调用」。
- **落点**：`~/.dsh/mcp-gateway/cordis.patch.yml` 的 `servers` 增 `openviking`（指向 `127.0.0.1:1933` 的 MCP 端点 / 或 openviking 的 stdio 桥）；同时把 `openviking-memory-runtime` 的 MCP 工具面从直连改为不挂（只保留 recall/capture/commit 的记忆旁路）。**注意**：memory 插件除工具面外还承担自动 capture/recall，这块要保留——只收编「工具列表」部分。
- **收益**：目录从 ~24 个工具降到 1 个入口，每步省 ≈1.5k–2.5k tokens；工具 schema 调用时才拉取。
- **风险/验证**：openviking 是记忆核心，改动需确认 MCP 端点稳定（health 工具）；改后新开会话验证 `mcp_gateway(tool=find/search/read)` 可用、记忆召回仍正常。

### 方案 A 的落地细节与卡点（已查证）
- openviking 插件 `index.mjs:113` 调 `mountOpenVikingMcp(ctx, config)` **无条件挂载 24 个工具，没有任何 config 开关可关或过滤**（`config.mjs` / `mcp-env.mjs` 只处理连接、recall、超时等）。
- `dsh-mcp-gateway` 只支持 **stdio** server（`command`+`args`，见 `lib/config.js`），不支持 http 直连；但 openviking 自带 `servers/mcp-proxy.mjs`（stdio 代理），理论上可作为 gateway 的一个 server 加进去。
- 记忆的 capture / recall / commit / skills 由 `runtime.mjs`/`client.mjs`/`skills.mjs` 走 HTTP 端点完成，**与 MCP 工具面相互独立**——所以「保留记忆、去掉 24 个工具」在语义上可行。
- **真正的卡点**：要让 24 个工具不出现，必须阻止 `mountOpenVikingMcp` 执行。三条路：
  1. **改插件源码**（profile 里是 registry 版 `@openviking/dsh-memory-plugin@0.5.33`，非本地 `file:`）→ 用 `pnpm patch` 打补丁，把 `mountOpenVikingMcp` 改成受 config 开关控制；同时在 gateway 加 `openviking` server。**工作量中等，可完全达成目标。**
  2. **上游提需求**：给插件加 `toolSurface: 'gateway' | 'direct' | 'off'` 或 `toolFilter` 选项，最干净，但要等发版。
  3. **暂不动**，接受现状（若 openviking 工具确实高频在用）。

> 结论：方案 A 是收益最大、语义正确的方向，但**不是改一行配置就能完成**——需要 patch 插件。是否投入取决于对「每步 1.5k–2.5k token × 全部会话」的量化收益判断。

### 方案 B（已排除）：config 内白名单收窄
经查证：openviking 插件**不提供**任何 allowTools/toolFilter 字段（`mountOpenVikingMcp` 无条件挂全量），故「改配置只暴露子集」这条路**走不通**，已排除，只能走方案 A（patch 插件）或上游加开关。

### 方案 C（P1，可选）：agent-team / session-query 场景化
- 平时用 `standard`；确有多 agent 任务时切到含 agent-team 的 preset。或把 `team_task_*` / `session_event_*` 合并成更少入口。
- 代价：preset 切换需新会话，且失去「同会话随时扇出」便利，**需权衡，不建议默认做**。

### 不建议做
- 删 `present`、`skill`、`web`、`fs`、`pwsh` 等高频核心工具：收益小（本就精简）、风险高（破坏日常工作流）。
- 在同一会话里中途改清单：直接打穿 prefix cache，成本反升。

## 5. 风险与回滚
- **openviking 是记忆核心**：任何改动都必须先确认 `127.0.0.1:1933` 健康（`health` 工具）；改后新开会话验证 recall 注入、capture 落盘、commit 正常，且 `mcp_gateway` 能列/调 openviking 工具。
- **prefix cache**：工具清单变更必须在新会话生效，绝不在当前长会话中途改（会打穿全段 cache，成本反升）；改完先重启 dsh web。
- **回滚**：所有改动集中在 `~/.dsh/profiles/web/cordis.patch.yml` + `~/.dsh/mcp-gateway/cordis.patch.yml` + `pnpm patch` 的补丁文件；回滚 = 还原这两个 yml + `pnpm patch-commit` 撤销 / 删 patch。改前各备份一份（参考现有 `.bak-*` 惯例）。
- **量化验证**：改前用 `token-optimizer` / `dsh-context` 投影缓存记一次 baseline（每步 catalog 未命中 token），改后同任务对比，确认实际下降。

## 6. 执行建议 / 下一步
按性价比排序，建议：
1. ✅ **baseline 已量化坐实**（§7）：toolsTokens=16,327，openviking 24 工具 ≈8.4k tokens（占 52%）。**结论：openviking 是最大且唯一值得动的一块，方案 A 性价比确定。**
2. **P0 二选一**：
   - 求稳 → 走**上游提需求**（方案 A-2），同时方案 C 不做；
   - 求快见效 → **方案 A-1（pnpm patch 插件 + gateway 加 server）**，工作量中等，收益确定（净省 ≈8k tokens/步）。
3. **P1（agent-team/session-query）暂不做**：除非有明确的「纯单线程任务占多数 + token 预算紧」证据，否则默认保留扇出能力。
4. 任何落地都遵守计划审批硬门（含代码/配置改动 → 先 Markdown 计划 → plan_review → 用户人工确认）。

## 7. 量化 baseline（token-optimizer / projcache 实测，2026-11-13）

数据源：`~/.dsh/storages/session_projcache/sessions/session-61be2a12-….json`（本体检会话）。

| 指标 | 实测值 |
|------|-------|
| **toolsTokens（工具目录每步固定占用）** | **16,327 tokens** |
| systemTokens | 2,081 tokens |
| messageTokens | 47,340 tokens |
| 本会话步数 / 缓存读 | 64 步 / 3.71M cacheRead |
| contextWindow | 1,000,000（压力 8.3%，健康） |

**OpenViking 24 工具精确体量**（直连 MCP `127.0.0.1:1933` 的 `tools/list` 实测，JSON schema 字节）：

- 合计 **33,790 bytes ≈ 8.4k–9.7k tokens**，占 toolsTokens(16,327) 的 **约 52%**。
- 头部重工具：`add_resource` 6802B、`write` 3263B、`search` 2796B、`add_skill` 2622B、`edit` 1693B、`set_acl`/`privacy_upsert`/`privacy_resolve` 各 1.2–1.4KB。
- 24 个里低/零频维护类占了近一半体量：`add_resource`+`add_skill`+`write`+`edit` = 14.4KB（多数会话用不到）；`privacy_*`+`*_acl`+`list_users/groups`+`cancel_watch`+`download` = ~8.3KB。

**结论（baseline 坐实）**：工具目录里**一半就是 openviking**。若改走 gateway（1 个 `mcp_gateway` 入口 ≈200 tokens + 按需 list），**净省 ≈8k tokens/步**。按本会话 64 步估算，单会话少发 ≈0.5M tokens 的 catalog 前缀（虽大头是便宜 cacheRead，但每步未命中部分、以及长会话累计仍可观）。**方案 A 性价比确定，值得做。**

> 一句话总结：**工具清单已相当精简，唯一值得动的是「让 OpenViking 24 个工具走 gateway / 或让插件支持关闭工具面」——实测它每步占约 8.4k tokens（全目录 16.3k 的一半），是唯一的大漏点，其余都是小修小补。**
