### 变更意图

在 `pickErrorMsgFromUrl` 中对最终 `raw` 再做一次 `decodeURIComponent`，并用 try/catch 在非法 `%` 序列时回退为原字符串，用于修复 SSO 回跳后提示仍显示 `%E4%B8%AD...` 或解码抛错导致无提示的问题。

### 行为与边界

| 场景 | 行为 |
|------|------|
| `null` / `""` | 提前返回 `""`，与原先空值逻辑一致 |
| `URLSearchParams.get("errorMsg")` | 已做一层 form-urlencoded 解码；再 `decodeURIComponent` 可处理**二次编码**（如仍含 `%E5%...`），这是本次修复的核心 |
| `vm.$route.query.errorMsg` | Vue Router 通常已解码；同样二次解码，行为与 search 路径一致 |
| `Array` query | 仍只取 `[0]`，再解码，未改语义 |
| 非法 `%`（如 `50%`、`a%b`） | `decodeURIComponent` 抛错 → 返回 `s`，避免整条 SSO 提示链路失败 |
| 已完全解码的中文/ASCII | 二次 `decodeURIComponent` 一般不变，无副作用 |

**二次解码的取舍（信息项，非缺陷）**：若业务希望展示的字面量里在「一层解码后」仍含合法 `%XX`（极少见），会被再解一次。SSO 中文错误文案场景下可接受。

**与 hash 路由**：`fromSearch` 只读 `window.location.search`；`#/login?errorMsg=...` 时依赖 `fromRoute`。这与 `handleExternalToken` 只看 `search` 的限制一致，属既有设计，非本 diff 引入。
