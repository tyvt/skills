会话027确认多模块共用弹窗从路由名推断 depositType 导致查空，修复为父页显式传 depositType prop（benefit→publicincome，renewal→continuouspayment），四个模块共用组件改一次覆盖。
# 2026-11-03 (Tuesday) ChatLog:
**user**: 【记忆类型】bug
【标题】多模块共用同一弹窗时，业务类型靠父页显式传 prop，禁止从路由名 / 目录名推断
【内容】情况：资金补交（supplement）、电梯缴存（elevator）、公共收益缴存（benefit）、续筹缴存（renewal）四个模块共用 maintenance/depositNotice/components/ 下同一套弹窗与缴存清册组件。弹窗要用 depositType 去查账户数据，原实现是从路由名 / 目录名反推，结果 benefit 推成 benefit、renewal 推成 renewal，而接口真正认的枚举是 publicincome / continuouspayment，查询恒为空——表现是「选完楼幢右侧表格空白」，而改组件样式、改边框都毫无效果，因为根本没发对参数。为什么：V3 里「薄壳入口页 + components 共享内核」是主流结构，一个组件会被多个业务线入口复用，组件自身不知道自己在哪个业务里，只能用路由/路径猜；而后端枚举名与前端目录名往往不是一套命名（目录名是人起的，枚举是后端定的），一旦不同源就静默错查。怎么做：① 共享组件只声明 props（此处 depositType），由父页（PaymentRangeTable）从自身模块常量显式下传，组件内不留任何路由/路径/目录名推断分支；② 顺带把同类大小写判断一起修（afterpayment / publicincome 必须与枚举完全一致）；③ 验收必须逐个入口各跑一遍（四个模块都要选幢后能看到数据），只测一个模块会漏掉三个。
【验证证据】会话 027 第 1 轮：用户报「电梯缴存、公共收益缴存、续筹缴存问题相同」；最终结论明确「新增 depositType 属性，由父组件传入正确的业务类型；修复原先从路由名推断 depositType 的问题（如 benefit → 应为 publicincome，renewal → 应为 continuouspayment），避免接口查询无数据」，并指出四个模块共用 depositNotice/components/ 下一套组件，改一次即可覆盖四个模块。
