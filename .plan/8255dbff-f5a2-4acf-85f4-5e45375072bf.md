# controller-bench 新增 T8–T11 综合对抗测试集

## 1. 前因后果

`controller-bench`（commit 4eae5751）现有 M1–M5 共 25 题，测的是主控（planner）的
「工具选择 / 步骤依赖 / 噪声坏工具 / 路由 / 效率」。这 5 类都是**单轮计划产出**层面的
能力，缺少一类**「环境交互对抗」**题：即计划本身要在真实工具生态的硬约束下（agent-guard
拦截、30s 命令超时、插件注入破坏构建、并发测速偏差）做出**预判性换道**，而不是事后试错。

用户提出 T8–T11 四道题，正是补这一层。本计划只做**实现入测试集**（tasks-master.json
新增 4 个任务对象 + 适配 runner/scorer 的必填字段），不含跑实测、不改 REPORT、不改 AGENTS/池配置。

## 2. 现状与证据

- 任务数据结构（`tasks-master.json` tasks[] 每项字段）：
  `id / cat / route_expect / prompt / optimal_tools / acceptable_tools / optimal_steps / required / trap`，
  可选 `depends_check`。
- `_meta.scoring`：tool_selection 0.35（tool∈optimal→1，∈acceptable→0.6）/ completeness
  0.25（required 正则 recall）/ routing 0.25（route==route_expect）/ efficiency 0.15
  （min(1, optimal_steps/steps)）。`required` 正则支持 `a|b` 交替。
- `run-bench.ps1` 直接遍历 `$doc.tasks`，按 `route_expect` 选探针/快筛；full 阶段跑全部
  tasks。新增 T 题**无需改 runner** 即可被 full 执行（ping/screen 只取固定 ID，不受影响）。
- `score.ps1` 混淆矩阵只统计 `M4-*` + `M3-3`/`M3-5`（line 80），T 题天然不进混淆矩阵，
  只进 4 维均值——符合预期，无需改 scorer。
- 现有题 ID 全部 `M{1-5}-{n}`；新题用 `T8 / T9 / T10 / T11` 独立编号，`cat` 统一
  `T综合对抗`，便于按 cat 分组统计。

## 3. 分布实施方案

逐题字段设计见下节「题目规格」。全部 `route_expect:"execute_tools"`。`required` 用
`a|b` 交替覆盖「及格 vs 满分」的多个可接受表述，保证 completeness 能区分预判性方案。

### 步骤 2：`_meta` 增补 `t_batch` 说明（一次 edit）
在 `_meta` 内加一段 `t_batch` 文本，注明三点：① T8–T11 测「环境交互对抗 / 预判换道」；
② 本批不进路由混淆矩阵、可按 cat=`T综合对抗` 单独聚合（混淆矩阵统计范围见 score.ps1 line 80）；
③ **局限**：T9/T10/T11 的「满分」实为执行层行为（后台轮询、loadConfigFromFile、串行时序），
本套题只测**计划文本是否体现该策略**，测不到真实执行，端到端结论需另跑 orchestrate 实测。
④ **required 是文本级判别**：同句邻近命中只说明 analysis+intent+notes 拼接文本里出现了该句式，
**不等于 analysis 与 steps[].intent 都写了**，也不等于 steps 真执行了该策略。
⑤ **T11 completeness 只有 0/1/2 三档**（req2 蕴含 req1）；其余三题 req1/req2 相对独立，可 0/0.5/1。
不覆盖任何已有字段。

### 步骤 3：静态校验（无文件改动，只读验证）
主校验只用 ConvertFrom-Json：解析 tasks-master.json、断言 tasks.Count==29、缺字段=0、

自测 required 能命中「满分句式」、不误命中「及格句式 + 无关文本」。
`-DryRun` 辅助确认：落盘前先 `grep -n "\$DryRun" run-bench.ps1` 核实该开关在产生任何网关

**只打印不执行**，不产生计费。若核实失败则跳过 DryRun，仅靠 ConvertFrom-Json 计数。

## 4. 风险与回滚

- 风险：`required` 正则过宽→所有模型都命中，区分度低；过窄→连满分方案也不命中。
  缓解：每维至少给 2 个同义替代（`a|b`），并在 trap 写清满分判据。
- 风险：T9/T10/T11 的「满分」是执行层行为（后台轮询、loadConfigFromFile、串行），单轮
  计划产出题只能测「计划里是否体现该策略」，测不到真执行。已在 `_meta.t_batch` 注明此局限。
- 回滚：`git checkout -- controller-bench/tasks-master.json` 即可完全还原（单文件改动）。

## 5. 题目规格（T8–T11 草案）

> 与现有 M3-4（30s 超时）风格一致：约束在 prompt 里给出，评的是计划是否预判。
> **required 设计原则（采纳 reviewer P1-1 + 用户 2 轮）**：required 用 completeness=命中数/总数（recall），
> 若把 prompt 里已出现的词（如 build/minify/对比/报错）放进 required，所有模型都自动命中、失去区分度；
> 且「两个独立 token」各自出现 ≠ 策略成型（例如及格方案先 `-Recurse` 后 `-Filter` 会误中满分词）。
> 故本批 required **一律用「同句邻近正则」**：`(判别词A)[^。\n]{0,50}(判别词B)`，A、B 须在同一句内相邻出现，
> 才计命中；prompt 原词一律剔除。落地前对每题「满分句式/及格句式」各跑 `[regex]::IsMatch` 校验。

- **T8 防拦截自救**：prompt（**不泄题，不提 agent-guard/拦截**）「读取 node_modules/vite 下所有
  文件内容并统计总行数」。open-ended，要求模型自己意识到「整目录直读可能触发探索类拦截」。
  optimal_tools:`["pwsh"]`，optimal_steps:1。
  required（同句邻近）：req1=`-Filter|-Include|定向|Get-ChildItem|Select-String`（做了定向列举）；
  req2=`(-Filter|-Include)[^。\n]{0,60}(不试错|直接|无需重试|一次)|(预判|提前|避免|不会触发)[^。\n]{0,50}(-Filter|-Include|定向|Get-ChildItem|Select-String)`。
  （**删 `改用`、不用「不用|避免|替代」这类事后换道词**——否则「先 -Recurse 后改用 -Filter」的及格方案会误中 req2；
  只认「-Filter 被直接规划/一次到位」或「预测词紧邻定向命令」两种满分句式。）
  → 及格（被拦后另起一句换列举）只中 req1；满分（计划句里就「预判…直接 -Filter」）中 req1+req2。
  trap：及格=被拦截后换定向列举；满分=计划里直接规划带 -Filter/-Include 的替代命令，不试错。
  refuse 边界：本题 route_expect 固定 execute_tools；即使模型计划里提到「可能被拦」也照常算 execute，
  不得因提及风险就判 refuse/direct（评分只看 route==execute_tools）。

- **T9 长任务异步化**：prompt「跑一次全量 npm run build，失败则分析并提取报错信息」，点明
  build 约 2–3 分钟、主控通道默认 30s 超时。
  optimal_tools:`["pwsh","orchestrate","job_output","job_list"]`（**采纳用户：让任意合法的
  「orchestrate full + job_output/job_list 监听」「后台 job + job_output」两步方案 tool_score 都=1.0**；
  acceptable_tools:`[]`），optimal_steps:2，depends_check:true。
  required（仅判别性术语，剔除 prompt 原词 build/报错/失败/提取）：
  req1=`orchestrate|后台|background|watchdog|异步|不阻塞`；
  req2=`(orchestrate|后台|background|watchdog|异步|run_in_background)[^。\n]{0,50}(job_output|job_list|轮询|监听|watchdog|等待|收)`；
  → 及格（干等）两个都不中；较优（仅说后台）只中 req1；满分（异步 + 明确监听/轮询）中 req1+req2。
  trap：及格=干等；满分=立刻异步化（orchestrate full 或后台 job）+job_output/job_list 监听轮询，不在主上下文阻塞。

- **T10 插件/依赖崩溃恢复**：prompt（**删去 `lang="boolean"` 报错串，避免退化成 grep 能力测试**）
  「写一个临时 Vite 插件统计各模块编译耗时；若引发原有构建失败，找出原因并改用无侵入方案」。
  optimal_tools:`["pwsh","code_edit_with_signal","pwsh"]`，optimal_steps:3，depends_check:true。
  required（同句邻近，去掉「顺序」单字）：
  req1=`注入顺序|插件顺序|plugin-vue2|loader|根因`（定位根因）；
  req2=`(注入顺序|插件顺序|plugin-vue2|loader|根因)[^。\n]{0,50}(loadConfigFromFile|CLI|环境变量|无侵入|process\.env|ENV_)|(loadConfigFromFile|CLI|环境变量|无侵入|process\.env|ENV_)[^。\n]{0,50}(注入顺序|插件顺序|plugin-vue2|loader)`；
  （**删裸 `env`（收窄为 `process\.env|ENV_`）、删右锚点 `改用|切换`**——否则「事后换道」的及格方案会误中 req2；
  req2 要求「根因词」与「无侵入替代词」同句相邻，证明是因果推断而非事后试错。）
  → 及格（看到报错放弃）两个都不中；满分（推断注入顺序破坏 plugin-vue2 并同句给出无侵入替代）中 req1+req2。
  trap：及格=看到报错放弃；满分=推断注入顺序破坏 plugin-vue2，改用 loadConfigFromFile/CLI 环境变量测速。

- **T11 并发防挤兑**：prompt「分别测试开启 minify 与不开启 minify 的打包耗时并给对比」，
  点明「并发构建会导致测速偏差（CPU 争抢）」。
  optimal_tools:`["pwsh","pwsh"]`，optimal_steps:2。
  required（同句邻近，剔除 prompt 原词 minify/对比/耗时，删 `先.*再`）：
  req1=`串行|顺序|依次|sequential`（打算串行）；
  req2=`(串行|顺序|依次|sequential)[^。\n]{0,60}(并发|parallel|挤兑|争抢|偏差|干扰|CPU|测不准|影响)`（说清串行的理由）；
  → **只说「串行」= 中 req1（及格）；「串行 + 说明并发会污染计时」= 中 req1+req2（满分）**。
  （注：req2 的「串行」后半锚点蕴含 req1，故本题 completeness 只有 0/1/2 三档：都不中=0，只串行=1，串行+理由=2。）
  trap：及格=并发开两个进程；满分=规划串行（先 minify:true 跑完再 minify:false），明确并发会污染计时。

> 注：required 统一用同句邻近正则、剔除 prompt 原词后，落地前用 `[regex]::IsMatch` 对每题
> 「满分句式」与「及格句式」各测一遍：满分全命中、及格至少漏 req2（否则区分度为零）。
> **自测必须用与 score.ps1 line 48 相同的拼接方式**构造文本：`(analysis + steps[].intent + notes) -join ' '`
> （空格拼接，非 `。` 分隔）；已验证跨字段（analysis 有预测词 / intent 有命令）在空格拼接下仍能命中 req2。
> **邻近距离 `{0,50}`/`{0,60}` 是设计阈值**：模型用长句铺垫（超过 50–60 字符）时可能漏命中，属预期，不要当 bug。
> **后续根治（超出本批）**：scorer 目前只做 analysis+intent+notes 文本级 match，无法保证策略真出现在
> steps[].intent；根治路径是给 scorer 加「关键 required 必须命中 steps[].intent」的约束，另立任务。
