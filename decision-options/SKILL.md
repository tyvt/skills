# 决策选项化

用户偏好：**凡是需要他做决定的地方，都给出可点击的选项，而不是让他在正文里找问题再手打答案。**

正文负责解释；决定通过选项框完成。两者不混。

## 核心规则

当一轮工作结束时，如果存在任何"需要用户拍板"的事项，**必须**调用 `ask_user_question`，而不是在正文末尾写"你想怎么办？"。

需要弹选项的典型情形：

- 下一步做什么（继续 A 还是先做 B）
- 方案取舍（两种实现路径二选一）
- 范围确认（这次改到哪里为止）
- 是否继续（长任务做到一半，要不要接着跑）
- 优先级（多个候选里先做哪个）
- 确认有风险的操作（删除、覆盖、批量修改）
- 缺失信息（需要用户提供路径、账号、选择）

不需要弹选项的情形：

- 纯汇报，没有待定事项
- 已经把所有工作做完，且没有后续分支
- 用户在上一轮已经明确指定了下一步

## 选项设计规范

1. **2-4 个选项**。一个选项没有意义，五个以上选择困难。
2. **推荐项放第一位**，标签末尾加 `（推荐）`。
3. 每个选项必须在 `description` 里写清**代价或影响**，一句话，具体到"会多花 2 小时""会生成 5 个文件""不可撤销"这种量级，不要写"更好""更简单"这种空话。
4. 选项标签要短，动词开头，能独立看懂。
5. **保留自由输入**：`ask_user_question` 本身支持 custom 回答，不要在正文里额外说"也可以自己输入"。
6. 多个不相关的问题可以一次调用传多个 question，但不要塞超过 3 个,否则用户要点很多次。

## 正文与选项的分工

正文里：

- 说清结论、数据、发现的问题
- 解释每个选项背后的取舍逻辑
- 不要重复选项的文字
- 不要在正文末尾再问一遍"你选哪个"

选项框里：

- 只放需要拍板的内容
- 每个选项自带一句代价说明

## 反面例子

不要这样收尾：

> 以上就是全部结果。你看要不要继续？如果继续的话，是想先做 A 还是先做 B？另外范围上要注意 C。

应该这样：

正文写完结果和取舍分析，然后调用 `ask_user_question`：

```json
{
  "questions": [
    {
      "id": "next",
      "header": "下一步",
      "question": "接下来做哪个？",
      "options": [
        { "label": "继续跑 A（推荐）", "description": "约 2 小时，产出最全，但会占用较多算力。" },
        { "label": "先做 B", "description": "约 20 分钟，快速验证方向是否值得投入。" },
        { "label": "暂停，我先看结果", "description": "保持现状不动，你确认后再继续。" }
      ]
    }
  ]
}
```

## 边界

- 不要为了弹框而弹框。没有真实待定事项时，正常结束即可。
- 不要用选项框替代本该说明的分析。选项是决策入口，不是省掉解释的借口。
- 有风险的操作要单独一个确认问题，不要和普通选择混在一起。
- 用户选了自定义回答时，按他的原话执行，不要硬套选项语义。

## 长期生效

这是一条长期偏好，不需要用户在每轮重复。除非用户说"不要弹选项了""直接说就行"，否则一直保持。
