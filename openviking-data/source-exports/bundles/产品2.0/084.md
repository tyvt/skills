## 结论

**会。** 原先逻辑是：

1. `query` 里有 `token` 时：先 `setToken`，再 **`createInstance()`**（约 208–211 行）。
2. 当 **`VITE_APP_IS_IFRAME != "1"`** 时：后面的 **`else` 里无条件再调一次 `createInstance()`**（约 232–233 行）。

因此「URL 带 `token` + 非 iframe」会 **连续挂载两次**，`#app` 上可能被挂两个根实例，行为异常。

iframe 场景下若 URL 已有 `token` 已挂载，父页面再通过 `postMessage` 带 `token`，`message` 里还会再调 `createInstance()`，也存在重复挂载风险。

## 修改说明

1. **只解析一次** `URLSearchParams`，用变量 `tokenFromUrl` 判断并 `setToken`。
2. **非 iframe** 时改为 **`else if (!tokenFromUrl)`** 再 `createInstance()`：URL 已带 `token` 并在前面创建过时，这里不再创建。
3. 在 **`createInstance` 开头** 增加 **`if (instance) return`**：避免 iframe 下「URL 已带 token 已挂载 + 后续 message 再带 token」时重复挂载。
