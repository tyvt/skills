## 问题根因

原先只有「看起来像数字 ID」的路径参数才会被移入 body（`isPathId`），导致大量接口仍把参数留在 URL 上，例如：

- `getByKey/qq.map.key`（带点号的配置键）
- `getBySecondVerifyLogCode/ABC123`（纯字母编号）
- `readXml/{deployId}`、`calculationChart/{id}` 等

## 全局修复策略

在 `normalizeTrailingPathParams` 中统一处理 **4 段及以上**路径：

1. **ByXxx 类动作**（`getByKey`、`getByComplexId` 等）→ 自动推断 body 字段名，**不再要求**必须是数字 ID
2. **已知单参数动作**（`readXml`→`deployId`、`calculationChart`→`decisionId`、`terminate`→`id` 等）
3. **多参数动作**（`listEffective`、`listReport`、`batchGenerateVoucher` 等）
4. **已规范的 V3 路径**（末段为 `/detail`）→ 跳过，不重复处理

## 覆盖的典型接口

| 类型 | 示例 | 规范化结果 |
|------|------|-----------|
| 配置键 | `/system/config/getByKey/qq.map.key` | POST `/system/config/getByKey` + `{ key: "qq.map.key" }` |
| 流程 XML | `/flowable/definition/readXml/{deployId}` | POST `/flowable/definition/readXml` + `{ deployId }` |
| 多参数 | `/evaluation/.../listEffective/{type}/{categoryId}` | body 含 `declarationType`、`categoryId` |
| 报表 | `/.../listReport/{planId}/{companyId}/{type}` | body 含三个字段 |
| 复杂 ID | `/property/company/getByComplexId/{id}` | body 含 `complexId` |

## 未改动的路径（刻意跳过）

- 已是 V3 格式：`/getEffectAgreementByAccountId/detail`
- 嵌套资源路径：`/benefit/dataSandbox/assetPanorama/operationalAsset`（无 trailing 参数）
- 中间带 ID 的子动作：`/workOrder/order/{id}/accept`（`{id}/子动作` 结构，需单独改造）

## 使用方式

现有 `$get('/xxx/getByKey/yyy')` 等写法**不用改**，拦截器会自动转换。刷新页面后看 Network，URL 应不再带路径参数，参数在 POST body 里。

若还有 400，把具体 URL 和 body 发我，可能是「ID 在中间、子动作在末尾」的特殊结构，需要单独加映射规则。
