## 为什么只快了约 2%？

生产 `build` 的大头不是「写 3000 个小 JS 文件」，而是 **把约 2700 个 `.vue` 各跑一遍流水线**：

- Vue 2 模板编译  
- Rollup/Babel 解析与打包（`build --profile` 里 `parse`、`loadBuiltinModule` 采样最高）  
- 少量 Sass / CSS  

`import.meta.glob` 即使用懒加载，**生产构建仍会为 glob 命中的每个页面生成模块并编译**，chunk 合并只减轻 **emit / 写盘**，**不会少编译页面**。所以 165s → 161s 是合理现象。

你们已经拿到的实质收益是：

| 指标 | 优化前 | 优化后 |
|------|--------|--------|
| `dist` 内 `.js` 数量 | ~3421 | **~523** |
| 日常 build 是否跑 visualizer | 是 | **否**（`npm run report` 才分析） |

部署、上传、浏览器请求碎片都轻很多，只是 **CPU 仍要啃完 2700+ SFC**。

## 还能做什么？（按投入 / 收益）

### 1. 配置级（低风险，通常 **5%～15%**，视机器而定）

- **`sass-embedded`** 替代 `sass`（Dart Sass 原生编译，大项目常更快）  
- **`maxParallelFileOps`** 提到 `min(64, CPU 核数 × 4)`（你这边 12 核，当前固定 20）  
- **`preserveSymlinks: false`**（少一层解析；若无 symlink 依赖可改）  
- **构建专用开关**：`FAST_BUILD=1` 时 SVG 跳过 SVGO、测试包关 `cssCodeSplit` 等（要接受产物差异）

### 2. 少编译页面（中风险，**可接近按比例缩短**）

`permission.js` 的 glob 仍会把 **全部 `views`** 打进构建图。若存在「某部署只上一部分子系统」：

- 扩展现有 [`VITE_APP_PROJECT_EXCLUDE_LIST`](env/.env)（或按子系统目录排除）  
- 让 glob / `external` **不纳入未部署模块**  

少编译 30% 页面，墙钟才有机会少 **大致 20%～30%**（非线性，但比调插件明显）。

### 3. 工具链级（高收益、成本高）

- **Vite 6 + Rolldown**：打包阶段常更快，**SFC 编译量不变**，整体常见 **10%～25%**，需升级与回归  
- **拆应用 / 模块联邦**：按业务域多个入口，日常只 build 改动的域  
- **预编译组件库**：把稳定 UI 打成独立包 + CI 缓存，主应用只编业务页  

### 4. 工程习惯（几乎零代码）

- CI **缓存** `node_modules/.vite`、依赖安装层（二次 build 略快，冷构建帮助有限）  
- 本机 **杀毒实时扫描** 排除 `node_modules`、`dist`（Windows 上偶发差一截）

## 结论

- **不是没空间**，而是：在「单仓库 + 全量 views glob + Vue2 SFC」架构下，**配置微调很难把 2.7 分钟打成 1.5 分钟**；要明显降墙钟，要么 **少编译模块**，要么 **换/拆构建链**。  
- 已做优化对 **产物体积、部署、CI 写盘** 仍然值得保留。

如果你愿意继续动刀，我建议优先两条里选一条：

1. **配置组合拳**（`sass-embedded` + 并行度 + 可选 `FAST_BUILD`），我可以在仓库里直接改一版并再测一轮耗时；  
2. **按部署裁剪 views**（例如只 build 苏州现网菜单涉及的目录），需要你说一下是否有「多环境 / 多子系统」的划分规则。
