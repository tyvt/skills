### 最终结论
已修复：苏服办 URL 中的 `token` 不会再被当作 `Authorization` 请求头发送。

### 问题原因

苏服办入口 URL 里的 `token` 仅用于 SDK（如人脸识别）和登录换票，但之前若被误写入 `userStore`（含本地缓存），请求拦截器会统一加上 `Authorization: Bearer {token}`，导致苏服办 token 被带到业务接口。

### 修改内容

1. **`api/index.js`** — 请求拦截器增加判断：若当前 token 与苏服办 URL token 相同，且为苏服办入口，则不添加 `Authorization` 头。

2. **`h5Context.js`** — 新增 `clearSfbTokenIfStored()`，在苏服办登录前清除误存的苏服办 token。

3. **`usePortal.js`** — 苏服办入口初始化时先清除误存 token，并始终走 `sfbLogin` 换取内部 `accessToken`（不再因本地已有 token 而跳过登录）。

4. **`sfbFaceAuth.js`** — 人脸识别只使用 URL 中的苏服办 token，不再回退到 `userStore.token`。

### 行为说明

- **苏服办 token**：仅用于 SDK / 登录换票，不出现在请求头。
- **内部 accessToken**：由 `sfbLogin` 返回后写入 `userStore`，正常用于后续 API 鉴权。
