### 最终结论
### 简单说结论

**因为 Tesseract 输出的内容里，根本就没有我们能可靠映射出的「数字 + 运算符 + 数字」信息**，所以在规则解析那几轮里，始终算不出结果，只能返回空。

结合你贴的日志来看：

```text
识别内容 = yee / CW
计算结果 = (空)
```

在当前 `parseCaptchaText` 里，大致会经历这几步：

1. **预处理+纠错后过滤**  
   - 先做一些通用替换：`O→0, L/I→1, S→5, Z→2, B→8, g/q→9` 等。
   - 然后用 `raw = raw.replace(/[^0-9+\-*/=?A-Za-z]/g, '')` 把非字母/数字/运算符都去掉。
   - 再尝试只保留数字和运算符，去提「一位数字 运算符 一位数字」：
     ```js
     code = tryParseExpr(raw.replace(/[^0-9+\-*/=?]/g, ''))
     ```
     但像 `yee`、`CW` 这样的串，去掉非数字运算符后往往就变成 **空串** 或纯字母，根本没有任何数字或 `+ - * /`，这一步自然返回空。

2. **字母→数字/运算符特定映射再试几轮**  
   - 针对我们之前见到的模式（`ELC`, `ENS`, `ETN`, `NA` 等）做了映射：
     - `E→8`、`L→*`、`C→1`，`ENS→8-5` 等。
   - 但现在出现的是 **`yee`、`CW`**：
     - `y`、`e`、`C`、`W` 目前都不在我们硬编码的映射里；
     - 即便强行加映射（比如 `C→*`、`W→某个数字`），也缺乏依据，很容易把完全不同的验证码误算对或误算错。

3. **最后退回纯数字**  
   - 取 `digits = raw.replace(/[^0-9]/g, '')`，但像 `yee`、`CW` 根本没有数字，所以还是空。

所以现在这几张验证码，对于 Tesseract 来说，已经“看不出任何数字和符号形状”，只剩下一堆字母阴影，这就超出了我们基于规则纠错的能力边界了。

---

### 这说明了什么？

- 我们已经：
  - 用 sharp 按高度 2–3 倍放大 + 灰度 + 可选 normalize；
  - 多轮 PSM（7/8）识别；
  - 多次重试不同验证码；
  - 按你给的规则做了「结构化解析 + 针对性字母映射」；
  - 打印每轮识别内容方便调参。
- 但仍然有不少验证码，Tesseract 给出的结果完全看不出算式轮廓（变成 `yee`, `CW` 这种），这说明：
  - **当前验证码的扭曲/噪声/字体，对通用 OCR 来说太难了**；
  - 在这种情况下，再加多少“猜测映射”也只是碰运气，很难把成功率拉到自动化可接受的水平。

---

### 实际工程建议

对现在这类验证码，要想 E2E 登录**稳定**，更现实的路径是：

1. **测试环境专用答案**（强烈推荐）  
   - 后端在 `/code` 的响应里（仅测试环境）加一个字段，如 `answer`，E2E 直接用这个字段填验证码；
   - 或者单独提供 `/test/code` 返回当前验证码的正确结果；
   - 有 `answer` 时完全跳过 OCR，OCR 只做演示/兜底。

2. **降低测试环境验证码难度**  
   - 测试环境换成**无扭曲的简单算式图**（不加波浪、扭曲、重叠），Tesseract 的识别率会立刻明显提升。

3. **继续保留当前 OCR + 规则纠错逻辑**  
   - 作为无 `answer` 时的备用方案；
   - 利用我们现在的「识别内容=… 计算结果=…」日志，偶尔调一调映射即可。

如果你同意，我可以下一步帮你**在前端 login 逻辑里预留对 `res.answer` 的支持，并在 E2E 中优先使用它**，这样只要后端在测试环境返回正确答案，你的自动化登录就会变得几乎 100% 稳定。

- **叶子点击只处理当前目录的“直接叶子”**  
  用 DOM 关系过滤：仅当某个 `sidebar-leaf-link` 的 `closest('[data-testid="sidebar-menu-item"]')` 等于当前 `menuItem` 时，才会被当作直接子叶子点击。  
  这样 `规约管理` 这一层就不会直接点到 `管理规约拟定`。

- **嵌套目录也只取“直接嵌套目录”**  
  `submenu.getByTestId('sidebar-menu-item')` 同样会拿到所有后代目录，所以我也加了过滤：只递归处理“上一层 `sidebar-menu-item` 祖先就是当前目录”的那些嵌套目录。

- **日志里体现层级**  
  递归时把标题拼成：`规约管理 > 管理规约`，方便你对照 DOM。

这样跑起来日志会变成类似：

- `[sidebar parent] 展开父级目录：规约管理`
- `[sidebar parent] 展开嵌套父级目录：管理规约`
- `[sidebar leaf] 点击叶子菜单（父目录：规约管理 > 管理规约）：管理规约拟定`

就和你贴的 DOM 层级一致了。
