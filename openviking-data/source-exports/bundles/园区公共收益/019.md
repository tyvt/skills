### 最终结论

## 原因分析

所有接口在 `request.js` 拦截器里都会调用 `getPageRequestHeaders()` 附加这些请求头：

```13:27:zhi2-web-admin/src/utils/pageRequestContext.js
/** 所有请求默认附加：zs-menu-name、zs-menu-path；有 ID 时附加 zs-data-id */
export function getPageRequestHeaders() {
  const meta = resolveRouteMeta()
  // ...
}
```

原先只从 `router.currentRoute.meta` 读取，在以下场景会拿不到菜单名：

1. **新增页**（路径以 `/add` 结尾）：当前匹配路由往往没有配置 `meta.title`
2. **新菜单**：只配了列表页，详情页 hidden 路由未配 `title` / `filePath`
3. **子路由**：叶子路由 meta 为空，但父级路由有配置

截图里「新增」操作的「操作模块」为空，而「修改」「删除」「审批」有值，正是这种典型表现——新增页路由 meta 未正确关联到菜单名称。

## 已做修复

增强了 `pageRequestContext.js` 中的 meta 解析逻辑，`resolveRouteMeta()` 会按优先级依次查找：

1. 当前路由 `meta`
2. `matched` 匹配链上的父级路由 `meta`
3. `/add` 或详情页路径 → 匹配同模块的 `detail` 路由
4. 从 URL 推断 `filePath`，在路由表和菜单树（`originalRoutes`）中查找

这样即使新菜单的详情路由没单独配 `title`，也能回退到列表菜单或同模块 detail 菜单的名称。

## 验证方式

在出现问题的页面（如新增保存）打开开发者工具 → Network，确认 POST 请求带有：

- `zs-menu-name`：如 `经营资源租赁合同详情`
- `zs-menu-path`：如 `benefit/resourcesLeaseContractFiling/detail`

如果请求头已有值但日志仍为空，则需要检查后端操作日志切面是否正确读取了这些 header。

## 后端建议

对于新加的菜单，仍建议在后台菜单管理中确保：

- 列表菜单配置 `菜单名称` 和 `组件路径`（如 `benefit/xxx/index`）
- 详情 hidden 子菜单配置 `菜单名称`（如 `xxx详情`）和 `组件路径`（如 `benefit/xxx/detail`）

这样前端和日志展示都会更稳定。
