- 修复线上多版本分支并存问题时，从最低版本分支（如 develop/v2.6.1）开始修复，不在当前高版本分支直接改。
- 修复完成后先把提交号与结果汇报给用户，等用户明确确认「没问题了」后才动手合并。
- 按版本链路顺序逐级 merge（如 v2.6.1 → v2.6.2 → v2.6.2-yulin），不得跳级或反向。
- 逐级合并时每个分支单独生成一个独立的 merge 提交，不在一个分支上一次性合入多级改动。
- 合并完成后逐个核对所有相关分支本地均已包含该修复提交，最后询问是否推送远程，不自行 push。
- 总结为用户明确偏好：改低不改高、先确认后合并、合并后全链核对。
- 若用户确认推送，在子模块 zhi2-web-admin 内用一条命令同时 push 三个分支（如 cd zhi2-web-admin && git push origin develop/v2.6.1 develop/v2.6.2 develop/v2.6.2-yulin），子模块最后停留在最末端分支 develop/v2.6.2-yulin。
