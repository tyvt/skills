【内容】什么情况：一个 bug 修复要同时进 develop/v2.6.1、develop/v2.6.2、develop/v2.6.2-yulin 三条发布分支，仓库是「父仓库 + zhi2-web-admin 子模块」结构，直接 merge 会带出大量冲突。

为什么：三条分支的基线差异很大，全量合并会把不相干的改动一起带过去；而子模块指针在父仓库只是一条 SHA 记录，cherry-pick 到子模块后父仓库不会自动跟，容易出现「父仓库还指着旧 SHA」或「yulin 分支指着主干 SHA」。

怎么做：子模块里在源分支做一次修复提交，另两条分支 cherry-pick 这一条，各得一个新提交号；父仓库在每条分支各做一次「只更新子模块指针」的提交，指针分别指向该分支上对应的子模块 SHA。yulin 这类业务分支要显式核对：如果第一次把指针指成了主干 SHA，需再补一次提交改成该分支自己的 SHA。收尾要报告三张表（子模块三分支的提交号 + 父仓库三分支的提交号与指针），并明确说明 env/.env 的本地代理配置未提交。
【验证证据】用户诉求「提交推送代码，并合并到262和262-yulin」。结论：子模块 develop/v2.6.1 dac8a93e7、develop/v2.6.2 fa00918cc（cherry-pick）、develop/v2.6.2-yulin 298ed67df（cherry-pick）；父仓库 develop/v2.6.1 09519a8、develop/v2.6.2 e4a0034、develop/v2.6.2-yulin d32ba38（子模块指针从 dac8a93 修正为 298ed67）。说明：env/.env 本地代理配置未提交；262 与 262-yulin 采用 cherry-pick 单条修复提交，避免全量合并产生大量冲突。
