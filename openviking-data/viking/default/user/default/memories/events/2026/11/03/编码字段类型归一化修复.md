# Summary
在苏住房G项目 zhi2-web-admin 中，阳光物业→协议管理→新增共管协议点保存直接抛后端异常 For input string: ""，前端无校验。根因为 subdistrictCode、communityCode、regionCode 等以 Code 结尾的字段后端是 Long，前端却填了中文名称或空串提交，Long.parseLong 抛 NumberFormatException；展示侧 formatter 改造只治理读未治理写。做法：提交前对 *Code 字段做类型归一化（非 /^\d+$/ 一律置空或取选择器 id），选择器同时维护 label 与 value 两份、提交只取 value，排错时先让用户贴后端 msg 定位具体接口。来源会话 a757e64c，基线 fb3e960。

【标题】保存报 For input string: "" 的根因：编码类字段（*Code）被填了中文名称，后端 Long.parseLong 炸在提交侧
【内容】什么情况：Web 后台（阳光物业→协议管理→新增共管协议）点保存直接抛后端异常 `For input string: ""`，前端无任何校验提示。根因不在展示层，而在提交侧：`subdistrictCode`、`communityCode`、`regionCode` 这类以 Code 结尾的字段在后端是 Long，前端表单却把它们当成「显示名称」来填，于是把「郭巷街道」「姜庄社区」这类中文串、或空串原样提交，`Long.parseLong` 立刻抛 NumberFormatException。
为什么容易踩：区划相关的 formatter 改造（展示侧统一到区级、拼接串换字典码）只治理了「读出来怎么显示」，没人管「写回去是什么类型」——同一批字段的展示与提交走的是两条独立链路，展示端做了归一化不等于提交端也做了。
怎么做：① 提交前对 `*Code` 字段做类型归一化，凡匹配 `/^\d+$/` 之外的值一律置空或从选择器的 id 取值，宁可空也不要送中文；② 选择器要同时维护 `label`（中文名）与 `value`（数字编码）两份，提交只取 value，禁止两个字段共用一个值；③ 排错时不要只盯前端——请求体看起来「字段都在」也可能全错，先让用户贴后端返回的 `msg`，并能明确指出需要看哪个接口的返回值（本例是协议保存接口的响应体，而不是详情接口）；④ 修复链路是多接口拼接：`getExtendedByComplexId` 补区域/街道/社区编码 → 账号详情取账号信息 → 网点列表反查网点 ID，任何一环缺失都会退化成空串。
【验证证据】用户诉求 1 报「新增共管协议，保存时提示异常」；诉求 3 的请求体里 `communityCode: "姜庄社区"`、`subdistrictCode: "郭巷街道"`、`regionName: "江苏省,苏州市,吴中区"`；诉求 4 修正后变成 `communityCode: "320506004006"`、`subdistrictCode: "320506004"`、`regionCode: "320506"`、`regionName: "吴中区"`，并在诉求 6 之后结论明确「之前导致 For input string: "" 的空 ID / 中文名称当编码的问题，在这份 payload 里都已消除」。
