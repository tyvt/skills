## 1. `source-exports/` 是规范目录吗？—— 不是
`openviking-data/` 的 `README.md` 明确写了它的契约：它是 `~/.openviking/data/` 的**纯镜像**，只含 `viking/default/user/default/**`（整棵用户树）、`vectordb/**`、`backend_meta.json`，外加脚本自己的 `.snapshot-meta.json`。`source-exports/` 是我为了满足「原始导出也纳入备份」临时塞进去的**外来目录**——它不是 OpenViking 的数据，恢复时复制回 `~/.openviking/data/` 也不会被识别，而且每次跑快照它只是被 `git add openviking-data` 顺手扫进去，并不属于被镜像的段落。所以它**违反了这个目录"纯镜像"的约定**。

（另：仓库里其实有两个备份目录——`openviking-data/` 是全量镜像+vectordb；`openviking-memory/` 只是 `memories/` 的扁平副本，方便人肉 diff。原始导出我放进了前者。）

## 2. 外部导入 vs DSH 内部对话提炼，区分开了吗？—— OpenViking 内部没有
我抽看了记忆文件的 frontmatter，只有 `directory:` 和 `generated_by:`（组件/触发），**没有任何 `source:` / `origin:` / `provenance` 这类来源字段**。我扫了 ≤400 个记忆：
- `source:` 命中 1、`origin:` 0、`imported` 0、`provenance` 0；
- `来源` 命中 15 个——但那是正文里的词，不是结构化标记。

也就是说：DSH 通过 `dsh-memory-plugin` 实时镜像进来的会话（在 `sessions/`）和经 `memory-migration` 从 cursor/workbuddy/opencode 蒸馏导入的记忆（在 `memories/`），在 OpenViking 里**混在同一个命名空间，系统不区分**。我加的 `source-exports/` 只是作为一个兄弟目录和 `viking/`、`vectordb/` 并列，所以它是" loosely 在镜像文件夹之外"，但位置仍然在镜像文件夹之内。

## 3. 需要区分吗？—— 我的建议
**原始源 vs 派生状态，应该分开**（这层最值得做）：把 `source-exports/` 迁出 `openviking-data/`，让后者保持纯镜像，原始导出单独成顶层目录。这样"蒸馏前的原始材料"和"OpenViking 派生出来的状态"边界清晰，恢复/重导也不会混淆。

**OpenViking 内部要不要给记忆打来源标记**（区分 DSH 原生 vs 外部导入），我建议**暂时不做**——那要改导入管线和插件、还要回填 6000+ 存量记忆，是另一个项目。而且你已经有"原始源归档"这个溯源安全网，重导随时能来，不急着在系统内部区分。
