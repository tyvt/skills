**编排器（`orchestrate`）本质是一个供 agent 主动调用的工具，不是会话的默认执行通道。** 现在的架构是：我（lead agent）收到你的任务 → 我自己用 read/edit/write/bash 干活，需要时才调 `orchestrate`。它没法通过一个开关变成「所有会话的所有编码动作都自动经过它」——那需要改 harness 的执行层，属于另一类工程。

不过如果你的目标是**「不想每次手动说『用编排器跑』，希望默认就走多模型池+故障转移」**，有几种可行做法，各有代价：

| 方案 | 做法 | 效果 | 代价/风险 |
| --- | --- | --- | --- |
| **A. 规则默认（推荐）** | 在 `AGENTS.md` 里加一条约定：编码/规划类任务默认先用 `op=full` 或对应 `op=tool` 走编排器，失败再回退直干 | 近似「默认走编排器」，跨会话生效 | 依赖 agent 自觉遵守规则；每个任务多一层编排开销、更慢 |
| **B. 我每轮自动判断** | 每次收到编码任务，我先判断复杂度，复杂就自动 `op=full`，简单就直接干 | 无需你提醒，且不浪费在琐碎任务上 | 仍在会话内判断，非硬性全量 |
| **C. 改 harness 执行层** | 把编排器接到 agent 主循环，让所有工具调用都过模型池路由 | 真正「所有会话默认」 | 改 DSH 内核，工作量大、影响全局稳定性，风险高 |

代价方面要提醒你两点：
1. **更慢、更贵**：`op=full` 会先规划再执行再汇总，多几轮模型调用；简单任务（改一行、读个文件）走编排器是浪费。
2. **不是硬开关**：A/B 都依赖 agent 行为约定，做不到「物理上强制」。真正强制只能走 C。

所以我的建议是 **A + B 组合**：写进规则「编码类任务默认优先编排器」，同时由我按任务复杂度判断，琐碎的直接干。这样既接近你要的默认效果，又不在小事上烧成本和拖速度。
