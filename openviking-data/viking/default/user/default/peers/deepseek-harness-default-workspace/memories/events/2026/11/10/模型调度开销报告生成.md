## 4. 性能：时间卡在哪里

实弹 162.7 秒里，PowerShell 本身（`Get-ChildItem`、`New-Item`、`Set-Location`、写一个 JSON）总共不到 1 秒，**99% 以上是模型往返**。10 次调用摊下来平均约 16 秒/次。

对比三次墙钟：4 步 mock 78.7s、4 步实弹 162.7s、2 步 mock 51.2s。2 步对 4 步大约成比例（5 次对 10 次调用），说明**延迟随「步骤数 × 每步 3 次串行调用」线性增长**，不是某一次调用异常慢。

按调用次数加权，162.7 秒的构成大致是：

| 环节 | 次数 | 估计占比 | 说明 |
|---|---|---|---|
| grok 审查 | 4 | **约 40%** | 次数最多的重模型调用，每次都是独立往返 |
| flash 生成命令 | 4 | 约 30–35% | 输出只有一行，但请求排队时间不比审查短 |
| grok 规划 | 1 | 约 15% | 一次，输出一个 JSON 数组 |
| auto 汇总 | 1 | 约 15%+ | 输入最大，生成最长的一段文字 |
| 真实执行 | 4 | < 1% | 可忽略 |

所以不是「Flash 生成命令太慢」单点问题，而是**每一步被拆成审查、生成、执行三次串行往返，审查和生成各占约三分之一到四成**。2 步任务 51 秒、4 步任务 163 秒，步骤数是第一放大因子。

## 5. 可降本的点

1. 审查结果是固定格式的一句话 JSON，但走的是最重的 grok-4.7 且每步一次。只读命令（`Get-ChildItem`、`git status --short`）可以走本地规则放行，省掉 4 次里的大部分。
2. 生成命令的输入每步都重发完整 `ENVIRONMENT_CONTEXT`，输出上限却是 512。这部分调用次数等于步骤数，缩步骤直接缩调用。
3. 汇总把所有回执原文回灌，是单次 token 最大的一次调用。只回灌每步的首尾几行就能砍掉大头。
4. 以上三点现在都能验证了：下次跑 `op=full`，返回 JSON 里的 `model_calls` 会给出每次的 `elapsed` 和 `usage`，stderr 里同步有 `[usage]` 行。
