## 优化点（按杠杆从高到低）

### 1. 开工查错 git 层级，前 8 步空转（最高杠杆）
- **现象**：step 1–8 一直在主 `zhi2-web-admin` 里找 flood/应急预案，全找不到；直到用户说"就在本仓库"才在 step 9 定位到 `worktrees/bug5897`。
- **根因**：step 2 只跑了 `git -C 苏住房G worktree list`（父仓库，只有主 checkout 一条），**没跑子模块** `git -C zhi2-web-admin worktree list`。flood 代码在子模块 worktree 里，父仓库列表根本不显示。
- **改法**：开工前置脚本改成固定两条——`git submodule status` + `git -C <submodule> worktree list`。或者第一次遇到"找不到模块"时，先 `git -C 子模块 worktree list` 再 grep。

### 2. 全仓 grep 打穿 prefix cache（18k 未命中主因）
- **现象**：step 5 对 `zhi2-web-admin` 全量搜 `login`，命中 250/376，spill 8KB；搜 `应急预案` 又全仓跑一遍。seq 29 直接报"上一步未命中 18k，极高"。
- **根因**：规则里"grep 优先限定目标业务目录"没生效——因为当时还不知道目标目录，就退化成全仓搜。
- **改法**：a) grep 前先判"模块在哪个目录"，判不出就走 orchestrate；b) 给 grep 工具加个封装，`path` 是仓库根或子模块根时直接拒绝并要求缩范围（机制强制，不靠自觉）。

### 3. reasoning 单步 ~10k，反复自我辩论
- **现象**：step 46 output 10,143、step 49 10,940、step 50 10,243 tokens，基本全在反复推演"根因是 AUTH 还是路径 doubling"，来回推翻十几轮。
- **根因**：缺真实 `PLAN_FILE_URL` 值，就在脑内演算，正踩 AGENTS.md 第 5 条"反复自我辩论说明缺事实，先调工具"。
- **改法**：a) reasoningEffort 已是 low 还不够，建议在系统提示或 cost-meter 注入硬约束："同一步内若第 2 次推翻自己结论，立即停并调工具"；b) 单步 output >3k 时由宿主强制截断/提醒。

### 4. 根因定位顺序反了：先推演后查值
- **现象**：step 40–47 一直在推理，直到 step 48 才查 `SELECT PLAN_FILE_URL ... FROM SERVICE_EXPAND.T_FLOOD_PLAN`，拿到 `/zhi2-dev/2026/...docx`（root-relative same-origin）后瞬间定论是 auth 问题。
- **改法**：定死流程"**症状 → 先查真实数据（DB/接口/日志）→ 再读代码**"。这条能直接砍掉 step 40–47 大半的 reasoning 和无效读文件。

### 5. DBX 踩了 DBX.md 已记录的坑
- **现象**：step 42 `T_FLOOD_PLAN` 没带 schema 报"无效表名"；step 44/45 `dbx_list_tables` 的 `%PLAN%`/`%FLOOD%` 两次返回一模一样的 `T_STD_EVAL` 表（pattern 被忽略），白跑两轮；最后 step 47 才用 `ALL_TABLES` 在 `SERVICE_EXPAND` schema 找到。
- **根因**：DBX.md 明写"Dameng 下 dbx_list_tables 的 pattern 会被忽略，直接查目录 SQL"和"describe 必须显式 owner"，执行时没照做。
- **改法**：把"找表"做成固定脚本（ALL_TABLES + LIKE），DBX.md 禁忌第 1 条就放"Dameng 找表先 ALL_TABLES 搜 schema"。

### 6. 大文件重复分段读
- **现象**：`detail-template.vue`（1404 行）被读 4+ 次（155-174、430-539、463-517、405-444），`zs-file-upload.vue`（453 行）整读+分段读，`resolveServerAssetUrl.js` 整读。
- **改法**：>300 行文件先 grep 定位函数名再 read offset/limit（这次已有部分这样做，但 detail-template 还是读了多段）。走 orchestrate 的 `file_reader` 更省。

### 7. worktree 建太晚
- **现象**：step 50 才 `git worktree add -b fix/bug6369-flood-plan-download`，前面 49 步都在 bug5897（别人的 worktree）里读代码。
- **风险**：虽然读的是 bug5897 代码（内容相同），但一直有"是否会污染别人 worktree"的顾虑，且 commit 时还得再确认。早建可避免。

## 机制建议（对应"规则进 AGENTS.md、机制进脚本"）

1. **cost-meter 升级**：现在 10k 只报"未命中极高"，应加一句"下一步：换 grep 缩范围 / 先查真实值再推理"，把建议和数字绑在一起。
2. **grep 封装拦截**：`path` 命中仓库根/子模块根时拒绝并提示"缩到 src/views/<模块>"，把自觉变强制。
3. **开工前置固定脚本**：`submodule status` + 子模块 `worktree list` + 各 wt `status --short`，一次跑完（skill 里其实已有，但这次没执行到子模块层）。
4. **DBX 找表脚本**：`ALL_TABLES WHERE TABLE_NAME LIKE` + 列 schema，替代被忽略的 `dbx_list_tables pattern`。
5. **reasoning 熔断**：单步 output >3k 或检测到"再次推翻上一结论"时，由宿主注入"停，先调工具"。
6. **交付前 token 自查**：收尾时跑 token-optimizer，这次停在 163k 未验收就收尾，应把"跑 optimizer + 对比未命中 TOP"写进收尾 checklist。...
