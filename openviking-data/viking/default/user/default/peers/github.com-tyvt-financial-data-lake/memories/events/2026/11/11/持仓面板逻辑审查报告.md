## 🔴 严重：会导致功能不可用或数据失真

### 1. 默认「本次投入 5000」+ `min_ticket=8000` + 按 `sh_ratio` 切资金池 → **默认永远买不了**

**位置**：`DEFAULT_RULES.min_ticket=8000`、`PLAN_AMOUNT_DEFAULT=5000`、`buildPlan()` 的 `pool`/`hardCap` 逻辑

**推演**（amount=5000，沪深都有候选）：
```
pool = {沪: 5000*0.6=3000, 深: 5000*0.4=2000}
hardCap = min(capRoom, indRoom, mktRoom, poolLeft) ≤ 3000
want = min(equalAmt, hardCap) ≤ 3000
if (want < 8000) → skipped.push(...); return   // 全部跳过
```
即使单边有候选（`otherHasCandidate=false` 借用对侧池），`poolLeft` 最多 5000，仍 < 8000。**amount < 20000 且双边都有候选时，推荐必然为空**。

**与文档矛盾**：README 写「月投 1 万买 2 只 → 每只 5000」，但 `min_ticket=8000` 下 1 万双边（沪 6000/深 4000）也买不了。

**修复**：三选一 —— ① `min_ticket` 默认降到 5000（与示例一致）；② 资金池不按 `sh_ratio` 预切，改为统一池 + 只数配额控制；③ 默认投入提到 ≥ 20000。建议 ①+②，并在「诊断」里明确输出「amount 不足 min_ticket×计划只数」的原因。

### 2. 持仓表占比口径（`T.mv`）与预警/买入推荐（`capitalBase`=`total_capital`）**不一致 → 误报超配**

**位置**：
- `renderHold`：`sharePct = r.mv / T.mv * 100`，`dev = sharePct - r.w`，`sharePct > max_single`
- `renderAlerts`：`CB = capitalBase(T)`（`max(total_capital, T.mv)`），`p = r.mv / CB * 100`

**触发**：未满仓时（`T.mv < total_capital`）。例：本金 10 万、市值 5 万、某只 1.3 万、`w=15%`
- 持仓表：`sharePct=26%` → 报「超配 11%」+「超单只上限」
- 预警：`p=13%` → 不报；`dev=-2%` → 不报

**影响**：同一只标的持仓表标红、预警不标红，用户无法判断该信谁；README 的「统一占比口径」修复只覆盖了预警↔推荐，**漏了持仓表**。

**修复**：持仓表 `sharePct` 改用 `r.mv / capitalBase(T)`，或在表头明确标注「占当前市值」并在 `dev` 徽章处用 `capitalBase` 口径（推荐后者，展示口径可保留组合内权重，但风控徽章必须统一）。

### 5. 编辑旧交易时**费用被按当前费率重算并覆盖**（违反 README「已存记录不动」）

**位置**：`openTrade()` 设 `$('#inFee').value = trade.fee` 后调 `updateTradeCalc()`；`updateTradeCalc` 中：

```javascript
if (!feeInput.value || feeInput.dataset.auto !== '0') {
    feeInput.value = amt > 0 ? autoFee.toFixed(2) : '';
    feeInput.dataset.auto = '1';
}
```
`dataset.auto` 初始为 `undefined`（`!== '0'` 恒真），编辑时 `trade.fee` 非空也会被 `autoFee` 覆盖。

**影响**：用户改了佣金费率后，打开一笔旧交易（只是看看）再保存，历史费用被改写，账实不符。

**修复**：`openTrade` 编辑态显式 `feeInput.dataset.auto = '0'`（视为手动值），或在 `updateTradeCalc` 中检测「正在编辑且用户未改费用输入」时跳过重算。

const YLD_WARN = (CFG && CFG.margin && CFG.margin.yldWarnPct != null) ? +CFG.margin.yldWarnPct : 20;

### 8. `perMktCapOf` 用 `ceil` 分配只数，**沪市可吸干全部名额**，与「沪深各 1 优先」不符

**位置**：`buildPlan()`

```javascript
const perMktCapOf = m => (hasSh && hasSz && maxBuys >= 2)
  ? Math.max(1, Math.ceil(maxBuys * (m === '沪' ? shW : 1 - shW)))
  : Infinity;
```
`maxBuys=2, shW=0.6` → 沪 `ceil(1.2)=2`、深 `ceil(0.8)=1`。沪两只高分候选先遍历，`items.length=2` 达上限，深候选被跳过 → **沪 2 深 0**。

README 写「默认 2 只，沪深各 1 优先」，实现是「按比例上限」，两者不等价。

**修复**：先给沪深各保留 1 个名额（`maxBuys>=2` 时），剩余名额再按比例；或 `perMktCapOf` 在 `maxBuys=2` 时恒为 1。

## 🟠 中等：逻辑正确性 / 一致性隐患

### 11. `recentTradeMap` 未来日期的交易会误触发护栏

```javascript
if (diff < 0 || diff > days) { if (!(t.code in map)) return; }
map[t.code] = { side, date, days: diff };
// 过滤：if (map[k].days > days) delete map[k];  ← 负数不会被删
```
若用户录了未来日期的交易（`diff<0`），且它是该 code 最新一笔，会进入 map 并保留（`-1 > 3` 为 false），导致「近 N 日刚买入/卖出」护栏误触发。建议 `if (diff < 0) return;`。

### 12. `totals` 中 `pnl`（仅有行情持仓）与 `cost`（全部持仓）**分母口径不一致**

```javascript
if (r.shares > 0) { cost += r.cost; hasPnl = true; }       // 全部持仓成本
if (r.pnl != null) pnl += r.pnl;                            // 仅有行情持仓盈亏
// pnlRate = pnl / cost
```
部分持仓无行情时，收益率被低估。建议分母改用「有行情持仓的成本」，或在 KPI 副标题标注「N 只无行情未计入」。

### 13. 超额卖出（脏数据）时**剩余费用被丢弃**

```javascript
const sh = Math.min(t.shares, p.shares);
const shareFee = t.shares > 0 ? t.fee * (sh / t.shares) : 0;
p.feeSum += shareFee;   // t.fee - shareFee 未计入任何地方
```
防御逻辑本身合理（不产生负股数），但 `feeSum` 会少统计。建议把剩余费用计入 `realized` 的扣减或单独记录。

### 14. `configStale` 之外，`loadMarginMetrics` **无并发限制**

`TARGETS.map(t => _mComputeOne(...))` 每只 3 个请求（2 kline + 1 JSONP），50 只 = 150 并发，易触发东财限流，导致「指标大面积未就绪」被整体降级。建议加 3~5 并发池。

### 15. `startApp` 中 `loadMarginMetrics` 完成后**重复渲染推荐**

```javascript
if (n) { render(); if (typeof renderPlan === 'function') renderPlan(rowsNow(), totals(rowsNow())); }
```
`render()` 内部已调 `renderPlan`；且两次 `rowsNow()`/`totals(rowsNow())` 重复计算。删掉手动 `renderPlan` 即可。

### 16. `#rsec` 显示值与 `startAuto` 实际间隔不一致

`$('#rsec').textContent = CFG.market.refresh_sec || 10`，但 `startAuto` 用 `Math.max(5, ...)`。配 3 时显示 3、实际 5。建议两处都用 `Math.max(5, ...)`。

### 17. `saveDiv` 再投资的 `maxSh` 费用估算偏高

```javascript
const maxSh = Math.floor((netDiv - calcFee('buy', netDiv)) / buyPrice / 100) * 100;
```
用 `netDiv` 当成交额估费用（费用偏大 → maxSh 偏小）。虽然保守，但提示的「最多可买」可能比实际少 100 股。可改为迭代 2 次或直接按 `netDiv/(1+费率)` 估算。

### 18. `meta[name=app-version]` 与 `const BUILD` 不一致

`2026.10.21.1` vs `2026.10.27.1`。若用于缓存控制，需同步；否则删掉 meta。

## ✅ 确认正确的核心逻辑（无需改）

- **移动加权成本**：买入 `cost += 成交额+费用`；卖出按均价结转、成本价不变；清仓归零；分红独立累计——与 README 完全一致。
- **多账户隔离**：`computePositions` 按 `acct|code` 分键，卖出校验按「账户+代码」净持仓，超额卖出按实际成交量计——健壮。
- **分红再投资校验**：100 整数倍、金额 ≤ 净额、日期 ≥ 分红日——逻辑完整。
- **行情双源回退**：腾讯 script → 东财 fetch，失败保留上次价格——符合设计。
- **配置以库为准**：`loadConfigFromDb` 首次导入、手动同步、`configStale` 横幅——框架正确，只是检测字段不全（见 #6）。
- **保存三重冗余**：内存 → IndexedDB mirror（带 `dirty` 标记跨刷新）→ 文件句柄；`dbStale` 时只写缓存不写盘——设计严谨，避免了「刷新丢数据」。
