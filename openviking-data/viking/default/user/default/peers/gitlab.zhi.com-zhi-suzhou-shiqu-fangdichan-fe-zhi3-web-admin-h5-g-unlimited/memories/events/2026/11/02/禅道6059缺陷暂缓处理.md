## 根因（已定位到具体一行）

`native call arrived after its batch was sealed` 不是 DSH 发出的，它来自 **cursor 通道插件** `@magpie-community/opencode-cursor-auth`：

`native-session.mjs` → `acceptCall()`：

```js
if (this.terminal || this.state === "awaiting-results")
  invalid("native call arrived after its batch was sealed", 502)
```

触发链路：

1. 某一步的工具调用数**等于**声明数时，`acceptCall()` 末尾调用 `sealBatch()`；如果这一步只有一个调用，第一条调用一进来就满足 `made == expected`，状态立刻变成 `awaiting-results`，批次封口。
2. 此时 Cursor 连接还没收尾，它会重传一帧**同一个 `ExecServerMessage.id`** 的 exec。
3. 去重依赖 `this.execs.get(call.requestID)`；如果首帧被丢弃、没有登记，`prior` 就是空的，代码继续往下，遇到封批守卫，抛出 502 —— **整轮报废**。

关键证据：守卫上方自己的注释写着「重传可能在本批封口后到达，要先校验身份，只有新 exec 才违反封批阶段」——但**代码没有实现它**。因此它并非偶发故障，而是稳定复现在「单调用步 + 该帧重传」这一组合上的设计缺陷。

从你的失败会话（`session-7ee64452`）可以看到典型痕迹：第 1 步有两个并行调用正常完成，第 3 步只发一个 `mcp_gateway` 调用，38 毫秒后就被判定封批，随后报错结束。

## 修复

把守卫拆成两段，让注释成真：

```js
if (this.terminal) invalid(...)            // Run 已结束：照旧致命
if (this.state === "awaiting-results") {
  const sealed = this.batches?.find((b) =>
    b.calls.some((c) => c.requestID === call.requestID && c.digest === digest))
  if (sealed) return                       // 已在封批里的调用被重传：丢弃，不结束本轮
  invalid(...)                             // 真正的新调用：照旧 502
}
```

**没有放松校验**：terminal 仍致命；真正的新 exec 仍 502；同 `requestID` 但 digest 变了也不放行。
