**接口**如果也改成纯相对（无前导 `/`，如 `api/version/...`），浏览器会相对**当前文档 URL** 解析。

但这里有个**致命坑**：uni-app H5 是 **hash 路由**，文档 URL 形如 `https://host/wechatapph5/#/pages/my`。相对路径 `api/version/...` 会相对 `https://host/wechatapph5/`（hash 不参与）解析 → `https://host/wechatapph5/api/version/...` ✅ 正确。

## 结论：可以改相对路径，但必须"相对文档 base /wechatapph5/ 解析"，而不是去掉前缀

改法有两种，我推荐**方案 A**（改动最小、和静态资源思路统一、不受 hash/history 影响）：

**方案 A（推荐）：接口前缀改为相对 `./api`（无前导斜杠）**
- `VITE_APP_PROXY_PREFIX`（production）：`/wechatapph5/api` → `./api`
- 请求 `./api/version/...` 相对文档 `https://host/wechatapph5/` 解析 → `https://host/wechatapph5/api/version/...` ✅
- 好处：**打包不再依赖 `/wechatapph5` 这个硬编码段**，换部署子路径（如 `/sz/`）也不用改代码；和静态资源 `./` 完全一致。

**风险点（必须说明）**：相对路径依赖**文档 URL 的目录层级**。
- 当前 hash 路由，文档恒为 `https://host/wechatapph5/`，相对 `./api` 稳定正确 ✅
- 若将来改 history 路由且深层路径（`/wechatapph5/pages/my`），`./api` 会错解析成 `/wechatapph5/pages/api` ❌ —— 但你现在是 hash，不受影响。

**方案 B（更稳，不依赖路由）：请求时用 `import.meta.env.BASE_URL` 拼**
- `BASE_URL` = vite base = `./`，可拼成 `new URL('api/...', import.meta.env.BASE_URL ...)`，但 `BASE_URL` 是 `./` 仍需相对文档，本质同 A；除非直接把 base 设成固定 `/wechatapph5/`（那就变回绝对了）。

**方案 C（最稳，彻底解耦）：固定取站点部署路径**
- 用 `location.pathname` 动态算出子路径前缀 + `/api`，不写死也不纯相对。适合路由模式将来会变的情况，但代码略重。
