# 决策列表查询
家园区一网通办新 app 与老安卓的决策列表查询条件一致，差异主要在列表返回后的展示逻辑。

## 查询规则
- 两端共用同一列表接口 `POST …/SmCastVoteListApp`，按 `type` 区分待完成和已完成。
- `type=0` 表示待完成，后端过滤 `busiState` 不在 `2,3`；`type=1` 表示已完成，后端过滤 `busiState` 不在 `0,1`。
- 主列表查询仍是同一套 `type=0/1`，不是新 app 另起一套查询维度。

## 请求参数
- 两端都有 `pageNumber`。
- 新 app 显式传 `countPerPage=pageSize`；老安卓模型未带 `countPerPage`，走后端默认每页条数。
- 两端 `interfaceVersion` 均为 `19000101`；新 app 由拦截器统一设置，老安卓在请求构造中设置。
- 后端支持 `keyword`，但新 app 列表页当前未传，老安卓未使用。
- 新 app 另外有 `SmCastVoteListAppHistory`，用于已完成列表里的“查看更多历史”；老安卓没有这条。

## 展示差异
- 新 app 在同一份列表数据上用 `voteState` 改主按钮文案，显示“参与”或“修改”。
- 老安卓同 Tab 主按钮只看 `pageType`，显示“前往”或“修改”；`voteState` 只影响状态和可点性。
- 进入详情调用 `SmUserVoteDetail` 改 `busiState` 后，两端都会刷新列表，条目从 `type=0` 池挪到 `type=1` 池，这是同一套 `type` 筛选下的状态变更结果。
