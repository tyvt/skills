### 1. 逃生舱 `# og:allow` 被模型自身可见可用 → "硬强制"目标自我瓦解（v2 新增，最严重）

§3.6 写"**拒绝文案里提示**可用 orchestrator-gate/bypass 标记（如命令首段加特定注释 `# og:allow` …）放行"，而拒绝文案正是以 `Error: <reason>` 返回给**模型**的（§2 源码依据）。这形成一个闭环：

> 模型第一次被拦 → 读到拒绝理由里"可以加 `# og:allow`" → 下一次直接在命令首段加上 → 放行。

"per-turn 首次"限制不改变性质——模型每个 turn 加一次即可，等价于无限次。这与文档开篇"**模式：B 硬强制**"和 §1"口头规则拦不住，需运行时硬拦截"的出发点**直接矛盾**：如果模型会自觉不滥用逃生舱，那它也会自觉走 orchestrate，本插件就不需要存在。

**建议（三选一）**：
- **A（推荐）**：逃生舱**不出现在给模型的拒绝文案里**，只在 DESIGN.md 给用户看；用户确需直跑时，自己改 config 或对模型明说"本次允许"。模型看不到 token 就不会自触发。
- **B**：逃生舱改为**用户侧动作**（UI 按钮 / 聊天里用户显式指令 / 临时 config），guard 通过读取用户态标记放行，模型无法写入该标记。
- **C**：删除逃生舱，仅保留 `enabled:false` 全局关；把"拒绝只是单次 isError tool 返回、不阻塞 turn、模型可改用合规写法"作为软逃生（这一点 §3.6 已提到，本身成立）。

另注：§4.2 拒绝文案模板里**没有** `# og:allow` 字样，与 §3.6 的"拒绝文案里提示"**自相矛盾**。两条必须对齐——建议按 A 方案，文案里不出现 token。

### 2. "只匹配命令首段" 存在 `cd … && npm run build` 前缀绕过（v2 新增）

§3.6 缓解措施 1："取 command 里第一条真正执行的指令（按 `;`/`&&`/`||`/`|` 切分后的第一段，且跳过 echo/… 等非执行头的段）"。

问题：skip 列表是 `echo/Write-Output/Write-Host/git/grep/Select-String/cat/Get-Content`，**不含 `cd` / `Set-Location` / `pushd`**。于是：

```
cd src && npm run build
```

- 切分：`cd src`、`npm run build`
- 首段 `cd src` 不在 skip 列表 → 视为"第一执行段" → 只检查它 → 不命中 build 规则
- `npm run build` 因"只匹配首段"**不被检查** → 放行

同理 `Set-Location x; npm run build`、`pushd x && pnpm lint` 均绕过。这是很自然的复合命令写法，模型（或用户）无需刻意规避就会踩中。

**建议**：把"只匹配首段"改为"**匹配所有执行段**（对每段判断首 token 是否在 skip 列表，跳过 echo/git/grep 等非执行头；对其余段做 build/lint 解析）"。这样：
- `cd x && npm run build` → `cd x` 不命中、`npm run build` 命中 → 拦 ✅
- `git commit -m "npm run build"` → git 段整体 skip → 不命中 ✅
- `grep "build" log` → grep 段 skip → 不命中 ✅
- `echo "npm run build"` → echo 段 skip → 不命中 ✅

配置项 `matchFirstSegmentOnly` 应改名为 `matchAllExecutionSegments`（默认 true），语义反转，避免沿用旧名继续埋坑。

### 3. "剔除引号内内容再匹配" 存在 `npm run "build"` 绕过（v2 新增）

§3.6 缓解措施 2："匹配前先剔除成对引号 `'...'` / `"..."` 内的子串再判定"。

问题：`npm run "build"` 与 `npm run build` 语义等价（shell 词法：引号只是分组，arg 值仍是 `build`），但按"剔除引号内子串"→ `npm run ` → 不命中 build 规则 → **放行**。同理 `npx "eslint" .`、`pnpm run "lint:fix"` 均绕过。

根因是把两种引号混为一谈：
- **shell 分组引号**（`npm run "build"`）：引号内是真实命令参数，**不能删内容**。
- **字符串字面量引号**（`git commit -m "npm run build"` 的 message）：引号内是数据，**应避免匹配**。

这两者在字符串层面无法用"全局剔除引号内容"区分，只有结合**段首 token 是否为 skip 列表**才能区分（见问题 2 的解法）。

**建议**：删除"剔除引号内子串"这条全局预处理。改为：
1. 先按分隔符切段；
2. 每段取**首 token（去 shell 引号后）**判断是否在 skip 列表，是则整段跳过；
3. 对非 skip 段做**词级 shell 解析**（按空白切词、去掉每个词两侧的配对引号、保留词内容），得到 argv 再匹配 build/lint。

这样 `npm run "build"` → argv `['npm','run','build']` → 命中；`git commit -m "npm run build"` → 首 token `git` → 整段 skip → 不命中。两个目标同时达成。
