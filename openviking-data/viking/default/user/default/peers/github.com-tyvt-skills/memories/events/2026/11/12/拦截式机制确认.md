**assistant [peer=github.com-tyvt-skills]**: 重要澄清：**不会自动经过编排器**。这两件事是分开的——

**插件目前做的是"拦截"，不是"改路由"。**

`orchestrator-gate` 是一个 `ctx.tools.guard` 守卫：它在**工具调用执行前**检查参数，遇到命中的操作（根 grep、整读大文件、账单命令、`npm run build` 等）就**拒绝并返回提示**"改用 orchestrate"。但它**不会**把这个调用自动转交给编排器执行——它只是拦下 + 告诉你"你应该去走 orchestrate"。

所以现状是：
- 模型**主动调用** `orchestrate` → 才会走编排器
- 模型想直接跑 `grep`/`read`/`build` → 被 gate 拦下，提示改走 orchestrate，模型再自己重发一个 `orchestrate` 调用
- **不是**"所有新对话自动进编排器"，也不是**所有**工具都经过它——只有那四类命中规则的命令会被拦

**另外两个边界要讲清**：
1. **不覆盖全部工具**：只有 pwsh/bash/terminal 命令类、`grep`、`read`、以及命中 build/lint 的命令会被检查；其它工具（edit/write/普通目录列举等）不经过该规则。
2. **`orchestrate` 内部不二次拦**（M1 已证）：编排器里的子工具在 `delegationDepth>0` 时直接放行，所以进编排器之后是真放行执行，不会死循环。

**要验证"是否真的生效在每条新会话"**，取决于插件是否在新会话的守卫链里——它随 Web 进程加载，理论上对所有会话生效（我这几个会话已实测被拦）。但它**不等于**"新对话默认走编排器"。

---

如果你的**真实目标**是"让所有重活默认、自动走编排器，而不是靠拦截后模型重发"，那需要的是**另一层机制**，不是这个 gate 能做的。可选方向：

- **A. 保持现状（拦截式）**：gate 拦 + 提示模型改走 orchestrate。模型会照做，但多一次往返。
- **B. 路由式**：在工具层把命中的调用**自动转发**给 orchestrate 执行并回填结果（改 guard 为"重定向"而非"拒绝"）。改动大、需处理结果映射与超时。
- **C. 规则式**：在系统提示/AGENTS.md 层面要求模型对这类任务先走 orchestrate（你已有 `dsh-token-policy` 的方向），不靠拦截兜底。
