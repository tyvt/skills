三、模型编排映射方案（把新测试题分给对的人）
结合实测结果与真实日志表现，我们可以重设编排器里的模型角色：

1. 执行类工具（对应 T8、T11 等沙箱防拦截场景）
主控模型（Deepseek-v4.1-flash）：由于它具有极强的“抗拦截能力”和“换道试错”属性，涉及探索、防御、不确定路径排查的动作（如 T8/T11），必须交回主控。

Code_edit_with_signal（Composer 2.5）：只接“确切要改什么”的任务。如果拦截规则需要改代码（比如加 agent-guard 的豁免），这种有明确 diff 的变更交给 Composer。

2. 执行编排层（对应 T9、T10 长任务配置修改）
plan_reviewer（Grok 4.7）：T10 这种“改配置导致全局崩盘”的复杂推演任务，最适合用长上下文、高逻辑审查能力的 Grok 4.7 做审核。

执行节点（Orchestrate Full / Team Lead）：

在 AGENTS.md 里强干预：凡是 npm run build/test 或者预计耗时 > 30 秒的动作，前置 Hook 或提示词必须强制它使用 orchestrate {op:"full"}。主控模型只负责发指令、轮询、和接收最后 200 字的报错摘要。

3. 探索型任务（对应 T10/T11 前置探路）
dsh-explore 只读子代理（推荐挂载 composer-2.5）：对于 node_modules 这种全是坑的目录，或者在排查前需要大量看源码的动作，可以直接派给无状态的探索子代理去跑。子代理不怕看错，也不怕把报错塞满上下文，它只把最终结论交回给主控。
