## 三个颠覆手交文假设的发现

**1. 「转交给 file_reader」根本不可行。** `src/graph.py:65-67` 与 config.yaml:47/58/81 都写明：file_reader / code_editor / code_edit_with_signal 是纯文本生成器，**没有磁盘读取权限**，读盘唯一途径是 `pwsh`——而 pwsh 在生产 85 次 execute 里只被选中 1 次。所以手交文设想的修复方向在能力上就不成立。

**2. 取证路径已打通（原以为要放弃）。** 手交文说 `session_event_search` 超时、建议放弃。实际上 orchestrator 的 `session_id` 就是宿主 DSH 会话 ID（`orchestrator/lib/index.js:39-47` 取 `exec.agent.id`），剥掉 `session-` 前缀后 **10/10 全部命中** DSH 会话目录。会话文件是多帧 zstd，按 magic 切帧逐帧解压即可；planner 答卷与 costs 行的 `ts` **delta=0s，15/15 精确对齐**。

**3. E3 的「prompt<400 = 没读大上下文」不成立。** #1–#5 的 prompt 只有 499–2082，但**计划全文本身就内嵌在里面**，completion 中位数 ~7000 是在写答案而非寒暄。

## 最值得改的一件事

`file_reader` 这个名字会让规划器误以为能读文件，而它实际没有读盘权限——**命名与能力脱节本身就是一个真实成因**。建议课题优先给「读盘类请求」补齐可用路径（要么把读盘写成 PLANNER_SYSTEM 的显式硬约束，要么造真有读盘能力的 file_reader 变体），而不是先改偏好措辞——那会让本来就该选 planner 的 6 条（40%）多花一轮。

另外还发现一个**成本漏洞**（不是路由漏洞）：#11/#12 是同一请求超时重试，15355 completion token 换来两份几乎逐字重复的答卷。

按此归因，「planner 占 50.6% 是浪费」应修正为真正失效约 4 条、占比 ~4.7%。
