## P1（严重）「计划」交给便宜模型产出 = 用短板补短板

流程是：便宜模型写 `plan.json` → 旗舰只做 PASS/REJECT。但**写 plan 本身就是架构类工作**——它要判定根因、选方向、识别契约，这恰好是日志里便宜模型最不擅长的部分（它把"校验 vs 不持久化"推了 4 轮内心戏）。

更麻烦的是旗舰被约束「不补方案」。于是：便宜模型写不好 → 旗舰 REJECT → 便宜模型重写 → 还是写不好 → 3 轮升级人类。人类拿到的是"一份写不好的 plan"，没法快速裁决，这一轮就废了。

**建议按风险分级，别一刀切：**
- **高风险任务**（多文件 / 涉及 auth·权限·资金 / 引入新外部契约 / 跨模块）：旗舰先出**「决策骨架」**（root_cause 方向假设 + 需核对的事实清单 + 方案方向 + 契约清单），**不写代码不写具体命令**；便宜模型据此补全 `explore` 的命令和 `edit` 的文件行。
- **低风险任务**（单文件、纯逻辑、无新契约，比如这次 6502）：**跳过旗舰审阅计划**，便宜模型直接按 plan-contract 出 plan 并执行，**只在汇报环节由旗舰复核**。省一轮，且这个任务本身就不值得让旗舰出骨架。

否则"所有任务都过旗舰审阅"会在简单任务上产生大量低质量 REJECT 轮次，成本反超"旗舰直接干"。

## P2（严重）`bun run typecheck` 被拦，砍掉了便宜模型的唯一验证安全网

这是你这次改动的副作用。逻辑链：
1. 项目里**没有 eslint**（package.json 无 eslint 依赖），`typecheck` 是唯一的静态自检手段。
2. 你把 `typecheck`/`tsc`/`vue-tsc` 纳入 `FULL_SCRIPTS` 后，`bun run typecheck` 走全量构建拦截路径。
3. 而 `orchestrate` 的 `pwsh` **没有本地 FS**（你日志里已验证），全量 typecheck 在 orchestrate 侧根本跑不了。
4. 结果：宿主直跑被 gate 拦，orchestrate 又跑不了 → **便宜模型只能放弃验证，报"未执行"**。

这比原来的"漏拦"更糟：原来至少还能自检，现在自检被禁，模型更容易在"未验证"的状态下声称完成。

**建议把 `typecheck` 和 `build/lint` 分开对待：**
- `build` / `lint`：成本大户、产物可缓存 → 拦，走 orchestrate。合理。
- `typecheck`：**验证安全网、单文件可窄跑** → 至少给「单文件/单模块 typecheck」豁免（`vue-tsc --noEmit <file>` 是窄命令）；全量 typecheck 允许后台 + 超时，不强制走 orchestrate。
- 退一步：若坚持全量 typecheck 也要拦，那必须提供「orchestrate 侧能跑 typecheck」的路径，否则就是死路。

本案例里那个 20+ 既有错误的 typecheck，本来就是个"能跑出基线"的动作，不该被当成成本敌人。

## P3（重要）汇报审阅的 Prompt 缺失

方案有 3 个审阅点：计划审阅（有 Prompt A）、人类审批（流程无 Prompt）、**汇报审阅（完全没有 Prompt）**。

汇报复核的逻辑和计划审阅**不同**——它不查"方案对不对"，查的是：**证据链是否完整、是否夸大、未执行的是否标注、`open_contracts` 的探测结果是否回填**。我上一轮建议"总结类由便宜起草 → 旗舰复核"，但 `dual-model-prompts.md` 里只有 A/B 两个 Prompt。需要补一个 **C：汇报审阅官 Prompt**，核心判据可以是：
- 每条"已完成"是否附了命令 + 输出
- 未执行的验证是否显式标注
- 有没有把"类型检查过"写成"功能已验证"
- `open_contracts` 里 `unverified` 的项是否在汇报里有对应说明

## 契约与流程的细节问题

**plan-contract.md**

| 问题 | 具体 |
|---|---|
| `acceptance` 缺"怎么算通过" | 只有 `check`，没有 `expected`。且**没处理既有基线错误**——本案例 typecheck 有 20+ 既有错误，若 acceptance 写"typecheck 通过"就永远不满足。建议 `acceptance` 加 `expected`（退出码 / 关键输出 / diff 行数 / 与基线的差集） |
| `commit` 的 `verify_with` 太弱 | `git status --short` 不判定"只改了 scope 内"。应升级为 `git diff --name-only`（或 `git show --stat`）**并与 `write_scopes` 做集合比对** |
| `open_contracts` 的 status 流转没定义谁改 | "探测是便宜的活，回填 status 也应是便宜做，旗舰复核"。文档只写了"命令通过后才可改 verified"，没写谁改、在哪一步改。建议：探测作为 plan 的一个 `decide`/`explore` step，执行后**由便宜模型回填**，旗舰在汇报复核时检查 |

**dual-model-prompts.md**

| 问题 | 具体 |
|---|---|
| R2 两处表述不统一 | 硬性条件是「REJECT」，但事实核对段又说「零引用 → 降级为探测」。旗舰可能直接毙掉，不给降级机会。建议明确：**R2 的 REJECT 是"改计划后再提交"，不是"终止任务"**，且 `must_verify_with` 必填 |
| R6 强制"探索决策拆分"在现实中太难 | 探索是渐进的、决策依赖探索、探索又依赖决策方向，强制线性拆分会让计划失真。建议改成：**`decide` 步骤必须声明 `resolve_by`，且 `resolve_by` 指向已完成的 `explore` 步骤或明确的事实来源**——用 DAG 依赖代替线性拆分 |
| "不补方案"的边界没写清 | 旗舰给"验证命令"算不算补方案？建议写明：**旗舰可以给"验证某事实的命令"，不能给"实现某功能的代码/步骤"**。否则旗舰过于保守，连 `must_verify_with` 都不敢给，便宜模型无从下手 |
| 循环终止不够细 | "3 轮"是每个审阅点独立计数，还是计划+汇报总共？REJECT 后是**全量重写还是增量修改**？建议：审阅点独立计数；**REJECT 后只允许改被点名的部分，已 PASS 的部分不许推翻**（防止便宜模型每轮推翻重来） |
| 人类审批缺"审批视图" | 人类看完整 plan.json 负担太重。建议约定：人类只看**旗舰输出的 `approved_scope` + `notes_for_executor` + 一句话风险摘要**，只回答"执行 / 打回补充 / 终止" |

**execution Prompt**

- 「违反即被 token-guard **折叠/拦截**」——折叠只是压缩，不是惩罚，措辞容易让模型误解为"折叠=失败"。改为"会被折叠压缩（信息不丢，但会拉长上下文）"。
