**assistant [peer=github.com-tyvt-skills]**: ## 分析结论：确实存在明显的「串行偏好」，且可量化

数据源：全部 652 个会话的投影缓存（与 dsh-context 面板同源），统计 orchestrate / spawn_teammate / workflow 的真实调用次数。

### 证据

| 指标 | 数字 | 解读 |
|---|---|---|
| orchestrate 使用过的会话 | **31 / 652（4.8%）** | 编排器几乎只在专项排查会话里被用过 |
| spawn_teammate 使用过的会话 | **37 / 652（5.7%）** | 子智能体也只在少数会话用过，且多为每次 spawn 1~4 个后即收 |
| 等效成本 TOP34 大会话中零编排/零子智能体 | **27 / 34（79%）** | 最烧钱的会话恰恰是最串行的 |
| 最近 7 天 equiv>1M 的 94 个会话中串行的 | **81 / 94（86%）** | 近期行为没有改善，还在加剧 |
| agentTeam 有成员的会话 | 37 / 1972 | 团队协作机制基本闲置 |

典型串行模式：`0f28a5ed`（1111 步，26.3M）、`fe39d020`（1307 步，1775 次工具调用，21.1M）——这类「批量导入/批量查询/逐 Bug 排查」任务天然可扇出，但全部由主模型单步单步做，缓存读和每步未命中被放大了几十倍。

### 根因判断

1. **AGENTS.md 已有「要执行动作一律 orchestrate」**，但没有「**何时必须扇出并行**」的判据——模型对「做 10 个同类任务」没有触发条件，只会循环 10 次。
2. spawn_teammate 的说明在系统提示深处，没有像编排器那样配硬门（orchestrator-gate），所以不遵守没有代价。
3. 缺「任务形态识别」：批量对象（多个 Bug、多个页面、多文件迁移）= 天然并行，没人提示模型先识别这个形态。

### 建议增强（写进 `~/.dsh/AGENTS.md`）

- **扇出判据（强制）**：同一动作要对 ≥3 个同类对象（多 Bug、多页面、多文件、多查询）执行时，必须先 `spawn_teammate` 扇出并行或 `workflow` 编排，禁止主模型循环串行；主模型只做汇总与验收。
- **长会话预警**：单会话 steps>300 或等效成本>5M 时，剩余任务必须改用子智能体并行拆片，不允许继续主循环。
- **team 硬门**：把 orchestrator-gate 的思路复制一份成「fanout-gate」——检测到连续 ≥5 次对同类对象的重复工具调用（如连续 read 不同文件）时拒绝并提示扇出。

要不要我把这几条规则实际写入 `~/.dsh/AGENTS.md`（以及可选地让 dsh_orchestrator_gate 插件加 fanout 检测）？
