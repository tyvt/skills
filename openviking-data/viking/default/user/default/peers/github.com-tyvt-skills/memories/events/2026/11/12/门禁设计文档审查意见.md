## 🔴 阻塞级

### 1. skip 列表与 §3.4 读取类规则冲突 → `.sessions` 账单查询可能漏拦（v3 新引入）

§3.6-1 定义 skip 列表：`echo / Write-Output / Write-Host / git / grep / Select-String / cat / Get-Content / rg / type`，并说"若首 token ∈ skip 列表 → **整段跳过**；否则做 §3.1 的 build/lint 解析"。

§3.4 读取类首 token 集合：`{cat, Get-Content, Get-ChildItem, Select-String, rg, grep, find, dir, ls, type}`。

**冲突**：`cat`、`Get-Content`、`Select-String`、`rg`、`grep`、`type` 同时出现在两个列表里。于是：

```
Select-String "cost" -Path .sessions/*.json
Get-Content .sessions/bill.json
grep "bill" .sessions/
```

- 按 §3.6-1，这些段首 token 在 skip 列表 → **整段跳过**；
- §3.4 本想拦它们 → 若 skip 先执行，**永远不会到达 §3.4** → 漏拦。

文档未说明 skip 的**作用域**：是"对所有规则整段跳过"，还是"仅对 §3.1 build/lint 跳过、§3.4 另行独立检查"？这是二选一的语义分歧，直接决定 §3.4 是否生效。

**建议**：
- 明确 skip 列表**只对 §3.1 build/lint 解析生效**（即"非 build/lint 执行头"），§3.4 对每段独立做首 token ∈ 读取类判定，不受 skip 影响。
- 或者更干净：把 skip 列表拆成两份——`buildLintNonExecHeads`（§3.1 用）与 `dataReadHeads`（§3.4 用），不要共用一个含混列表。
- 并在 §7 增加 selftest 正例：`Select-String x .sessions`、`Get-Content .sessions/y` 必须被 §3.4 拦截。

### 2. `statSync` 的路径基准与 `cd` 前缀不一致 → 单文件判定误判 / fail-open（v3 新引入）

§3.1 eslint/tsc 放行依赖 `fs.statSync(p).isFile()`；§3.3b 也依赖 `fs.statSync(file_path).size`。但 `statSync` 对**相对路径**按**进程 cwd** 解析，而命令段的实际工作目录可能因 `cd` 前缀而不同：

```
cd packages/app && npx eslint src/foo.ts
```

- 切段后检查的段是 `npx eslint src/foo.ts`；
- `statSync('src/foo.ts')` 相对进程 cwd（仓库根）解析 → **文件不存在**；
- 两种后果都坏：`isFile()` 返回 false → 视为非单文件 → **误拦**（本该放行的单文件 eslint 被拦）；或 `statSync` 抛 `ENOENT` → 被 §4.1 的 `catch` 捕获 → `counters.errors++` → **fail-open 放行**（若这是 build 段则漏拦）。

即：**同一机制在两个方向上都会出错**，且错误方向取决于 statSync 抛异常还是返回 false。

**建议**：
- 明确定义 statSync 的基准目录：优先 `exec` 上下文的工作目录（若可得），否则**不做 statSync 单文件放行**——即"存在 `cd`/`Set-Location`/`pushd` 前缀的复合命令段，单文件放行一律不适用（保守拦）"。
- §3.3b read 通常传绝对路径，风险低；但应在文档注明"仅对绝对路径做 statSync 门禁，相对路径按保守拦处理"。
- 把"statSync 基准与 cd 前缀"加入 §7 实测/实现注意项。

## 🟠 重要级

### 3. 外壳包装绕过未列明（硬强制的边界）

v3 的 argv 解析只识别"首 token ∈ {npm, pnpm, yarn, npx, eslint, tsc, vue-tsc, vite, 直接 bin}"。以下写法首 token 不在识别列表也不在 skip 列表，会**静默放行**但实际执行 build：

- PowerShell 调用运算符：`& npm run build`、`& "npm" run build`（首 token `&`）
- 进程启动：`Start-Process npm -ArgumentList "run","build"`（首 token `Start-Process`）
- 外壳：`cmd /c "npm run build"`、`bash -c "npm run build"`、`pwsh -Command "npm run build"`
- 脚本执行：`.\build.ps1`、`sh ./ci.sh`

这些不是"刻意规避"才会用的写法——`&` 和 `cmd /c` 在 PowerShell 用户里很常见，`pwsh -Command` 是嵌套调用的自然写法。

**建议**：至少在 §6 风险表新增一行"外壳包装绕过（`&`、`Start-Process`、`cmd /c`、`bash -c`、`pwsh -Command`）——已知限制，不覆盖；如需覆盖，递归解析参数串"，把边界讲清楚。**不建议**现在就实现递归解析（复杂度爆炸），但**必须列明**，否则读者会误以为"硬强制"无死角。

### 4. "用户侧显式授权"缺乏实现机制，且模型能否改 config 未确认

§3.6-3 说"用户确需直跑时……在聊天里显式授权本轮某命令——guard 不读任何模型可写入的标记"。两个空白：

- **机制空白**：模型如何在命令里体现"用户已授权"？如果模型在命令里加任何标记，那标记就是"模型可写"的，与上一句"不读模型可写入的标记"矛盾；如果不加标记，guard 又如何知道用户授权了？这句话当前**不可实现**。
- **config 可写性**：`cordis.patch.yml` / `config.enabled:false` 若模型有文件写权限，模型可以自己改 config 来关规则 → 绕过。需确认模型对 config 的写权限，并在文档写明"逃生舱仅在模型无 config 写权限时成立"。

**建议**：把"聊天显式授权"降级为**用户操作说明**（用户对模型说"本次允许"，模型仍需走 orchestrate，或用户手动改 config），**不承诺 guard 层有感知机制**；并在 §7 增加一项"确认模型对 config/插件目录的写权限"。

### 5. §3.2 repoRoots fallback 过粗 → 深层 path 的 grep 可能误拦

§3.2："repoRoots → exec workspace root → 都取不到时保守 fallback：视为仓库根 → 拦"；"命中：path 缺省/空/`.`/等于某个 repoRoot 前缀"。

若 repoRoot 取不到，`grep x src/views/mod` 的 path 是相对路径，无法与"仓库根"比较——若实现把它当作"path 等于 repoRoot"处理，就会**误拦所有 grep**，与"低误伤"的灰度定位冲突。

**建议**：fallback 分支只拦"path 缺省/空/`.`"这三类**明确根级**形态；对非空相对路径，保守**放行**并计 `counters.errors++`（提示 repoRoot 缺失），而非一律拦。把"取不到 repoRoot 时是否全拦"作为显式配置项。

### 6. `wholeReadMemo` 可变 Map 与"纯函数"声明矛盾

§4.1 注释："纯函数，selftest 直接覆盖。ctx 提供只读记忆集/统计，避免全局可变状态混入纯函数判定"，但签名传入 `wholeReadMemo: sessionWholeReads` 是 `Map`（可变），decideInterception 内部要读**和写**（3.3a 记"已完整读过"）。声明与实现不一致。

**建议**：要么承认它不是纯函数（改为"无 IO、仅依赖入参"），要么把记忆集操作外移（guard 回调里读/写，decideInterception 只接收"是否已读过"的布尔），保持 selftest 可测。

## 🟡 建议级

- **§9 仍写"§7.7"**（v2 已提，未修）：§7 无编号子节，应改为"§7 误伤样本那条"。
- **`tsc foo.ts` 不带 `--noEmit` 被拦**：§3.1 口径"仅当 `tsc <file.ts> --noEmit` 放行"，则 `tsc foo.ts`（单文件编译、输出 js）被拦。单文件编译属窄操作，建议加配置 `allowSingleFileTscNoEmit:false` 可调，或说明"单文件编译走 orchestrate 的成本可接受"。
- **§3.1 npx 直接 bin 的歧义**：`npx eslint .` 与 `npx eslint`（无位置参数）都要拦，需确认解析里"npx <bin>"后接位置参数的识别；`npx -y eslint .`（`-y` 选项）也要剥掉选项再取 bin，文档未提 `npx` 前置选项的处理。
- **§7 "token-guard 阈值已核实"** 写得好，但 §3.3b 的**字节阈值**（60KB/40KB）与 token-guard 的**行数阈值**（500/300）是两套口径，文档已说明"目标一致"，可接受；建议补一句"字节阈值对应的典型行数（.vue 约 60KB≈400~600 行）"帮助读者判断保守程度。
- **§4.1 skeleton**：`normalizeConfig` / `log` 标注"照 cost-meter 范式省略"可接受，但 `counters` 定义在 `apply` 内、`decideInterception` 无法自增——如果 selftest 要断言计数，需把 counters 设计成可注入或返回结构。

## 结论

**v3 已修复 v2 三个阻塞点，主体可推进，但落地前必须再处理两处硬伤**：

1. **明确 skip 列表的作用域**——只对 §3.1 生效，还是对 §3.4 也生效？当前含混会导致 `.sessions` 查询漏拦。建议拆成两份非执行头列表。
2. **`statSync` 基准目录**——相对路径 + `cd` 前缀会导致误拦或 fail-open；保守做法是"有 cd 前缀的段不做单文件 statSync 放行"，或取 exec 工作目录。

此外，**外壳包装绕过（`&`/`Start-Process`/`cmd /c`）应在 §6 风险表列明为已知边界**，避免"硬强制"被误解为无死角；"用户侧显式授权"需补机制或降级为用户操作说明。

修订后按 §9 流程建四件套，selftest 优先覆盖：skip/§3.4 冲突正反例、`cd x && eslint y` 路径基准用例、外壳包装样本（作为已知放行的回归基线）。§7.4（子 ctx 是否触发 guard）仍是首个实测项，结论前不开 `blockBuildLint` 的判断正确。
