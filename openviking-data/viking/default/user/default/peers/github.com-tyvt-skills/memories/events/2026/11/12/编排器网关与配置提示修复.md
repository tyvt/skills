## 诊断结论

**根因：不是编排器坏了，也不是模型坏了 —— 是把「要执行命令/构建」的活错误地投给了 `orchestrate op:"tool"`，而 `op:"tool"` 根本不执行命令。**

证据链（全部来自 `session-26c1c52d` 完整事件流）：

1. **编排器只被调 1 次**（57 次工具调用中）。其余 56 次——18 次 pwsh、13 次整读、grep、edit、write——全是主模型 `auto/hy3` 亲自干。所以「消耗几乎都在主模型、dsv4.1-flash 只占一小部分」成立：编排器子进程本会话只烧 **577 tokens / 5.35s**，宿主 hy3 烧了 **2.14M + 47.5k**。

2. **那唯一 1 次是 `{"op":"tool","tool":"pwsh","request":"跑 bun run build"}`**，返回的是 deepseek-v4.1-flash 的散文：「我没有直接访问你本地文件系统或执行命令的能力……以下是你自己执行的方法」。**构建根本没跑。**
   - 代码层：`api.run_tool→router.run_tool` 只做一次文本补全（`_call_once`）就返回，**没有 `_run_pwsh`、没有安全审查、没有执行**。只有 `op:"full"` 的 graph 路径（`_run_pwsh`）才真的 `subprocess.run` 执行 pwsh。
   - 「编排器无法正常工作」的真相：`op:"tool"` 被当成执行器用了，它只是纯文本模型，如实说「没执行能力」是对的。

3. **为什么拖到 765 秒 / 38 步**：build 没跑成 → 宿主降级为主模型全手动执行 → 34 个 reasoning 块、14.1 万字符推理 + 6.7 万字符工具输出塞进上下文 → 慢且贵。`orchestrator-gate` 还把宿主往 orchestrate 赶，但 `op:"tool"` 接不住执行，形成夹缝空转。
