## 二、针对 DSH 的具体建议

按 ROI 排序：

### P0：把"警告"变成"硬中断"

**1. reasoning 硬上限 + 强制工具门**
- 现状：cost-meter / reasoning-watchdog 只发 notice，模型读到后往往继续推理（`seq 129→146→159` 连续三步）。
- 建议：在 step 边界统计 `reasoning tokens > N`（如 2000）且 `tool_calls == 0` 时，**直接中断该 step 的 reasoning 生成**，注入一条强指令（"立即调用工具取事实或直接下结论"），而不是旁路 notice。DSH 已有 step 边界概念，实现成本低。
- 可配套：对同一 step 第二次触发时，直接以"未完成"结束该 step，逼模型下一步必须动工具。

**2. grep 工具层限域**
- 现状：`src/**` 全量 grep 能被放行，只在事后被 cost-meter 骂。
- 建议：grep 工具检测 `path` 为仓库根或 `src`、且 `pattern` 含 `|` 或宽泛词时，**返回拒绝 + 提示"先指定模块子目录或更窄 pattern"**，不执行。或在参数校验阶段要求 `path` 至少两级。
- 这比"事后警告"有效得多，因为模型对工具返回的硬失败更敏感。

**3. 截断结果自带下一步指令**
- 现状：dbx 返回 `[...chars 0..200; next cell_char_offset=200]`，模型还要自己想起 UNION ALL。
- 建议：`dbx_execute_query` / `read` 检测到 cell 或文件被截断时，**在 tool result 末尾直接追加**："该列被截断，请用 `UNION ALL SELECT SUBSTRING(col,n,180)` 分段，或改用更窄查询。" 把技能里的规则下沉到工具输出。

### P1：去重与预检

**4. Vision 结果按图片哈希缓存**
- 建议：`analyze_image` 对同一 `image`（fileID 或内容哈希）在同一 session 内第二次调用时，返回**缓存摘要 + "如需更细可指定 prompt"**，或直接提示"该图已分析过，见上文"。22340 的两次全页分析可省一半。

**5. commit/build 前 pre-flight 钩子**
- 建议：DSH 在 `git commit` 或 `npm run build` 前自动跑一次轻量探测：读 `package.json` scripts、检查 `eslint.config.*` 是否存在、检查是否有 `vue-tsc`。若缺失，**在工具调用前就提示**，避免 `seq 193` 那种无效 eslint。

**6. read 大文件护栏**
- 建议：`read` 目标文件 >200 行且 `offset/limit` 未指定时，返回提示"文件较大，建议先 grep 定位后带 offset 读取"，或强制要求 limit。可显著减少 `seq 111/116/118` 的重复整读。

### P2：成本计量与压缩

**7. cost-meter 归因到"模式"而非"步"**
- 现状：只报"上一步未命中 17k"。
- 建议：区分归因——`reasoning_bare`（空转）、`wide_grep`、`repeat_read`、`vision_repeat`，并在 notice 里给对应的一句话修复建议。模型看到"你这是 repeat_read，请用 offset"比"未命中 17k"更能改变行为。

**8. 压缩触发点前移**
- 本会话 `seq 285` 才 compaction，此时上下文已因 reasoning 和重复读取膨胀。建议在 **reasoning 占比 > 某阈值**或**连续两次 cost-meter 警告**时主动触发 compaction/裁剪，而不是等 token 总量到顶。

**9. 规范下沉为工具约束**
- 技能里的规则（DBX 分段、禁止全量 grep、构建在 commit 后）目前靠模型"记得读 references"。建议 DSH 把高频规则做成**工具级前置校验或结果后置提示**（见 2/3/5），让规范不依赖模型自觉。
