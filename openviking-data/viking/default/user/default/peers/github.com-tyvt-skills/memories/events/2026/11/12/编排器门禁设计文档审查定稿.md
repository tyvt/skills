## 🟠 重要级（需修）

### 1. §3.4 第一条规则"任一 argv 元素含 cost_bill.py → 拦"无首 token 限制 → `echo cost_bill.py` / `git commit -m "cost_bill.py"` 被误拦（v3 遗留、v4 未修）

v4 §3.4：

> 只要任一 argv 元素含 cost_bill.py → 拦。
> 或者：首 token ∈ 读取类 {cat, Get-Content, ...} 且任一 arg 的路径片段含 .sessions → 拦。

**第一条规则没有首 token 限制**，于是：

```
echo cost_bill.py                        → argv ['echo','cost_bill.py'] → 含 cost_bill.py → 拦 ❌
git commit -m "fix cost_bill.py crash"   → 含 cost_bill.py → 拦 ❌
Write-Output "see cost_bill.py"          → 含 cost_bill.py → 拦 ❌
```

v4 拆两份列表的意图是"cat 对 §3.1 skip 但被 §3.4 命中"，这个意图在第二条规则（读取类 + `.sessions`）上是对的；但第一条规则完全没利用任何 skip 列表，变成了"只要命令串里出现这个文件名就拦"，与 §3.6 整节的误伤控制目标自相矛盾（§3.6 明确把 `echo`/`git`/`Write-Output` 列为"数据/打印，不判定"）。

**建议**：§3.4 对每段先做"是否非执行头"判定，再进入两条子规则：

```
对每个段：
  if 首 token ∈ buildLintNonExecHeads && 首 token ∉ dataReadHeads:
      跳过（echo/git/Write-Output/Write-Host 等纯数据/打印段）
  else:
      if argv 含 cost_bill.py → 拦                  # python/py/pwsh -File 等都走这里
      if 首 token ∈ dataReadHeads 且任一 arg 含 .sessions → 拦
```

验证效果：

| 命令 | 首 token | 判定 |
|---|---|---|
| `python cost_bill.py` | python（∉两个列表） | 含 cost_bill.py → 拦 ✅ |
| `cat .sessions/bill.json` | cat（∈dataReadHeads） | 读取类 + .sessions → 拦 ✅ |
| `echo cost_bill.py` | echo（∈buildLint 且 ∉dataRead） | 跳过 → 放行 ✅ |
| `git commit -m "cost_bill.py"` | git（∈buildLint 且 ∉dataRead） | 跳过 → 放行 ✅ |

### 2. §4.2 文案"或在对话中显式授权"与 §3.6-4"guard 不读标记"直接矛盾（v4 遗留）

- §3.6-4：**"用户若确需直跑，只能自己改 config……再让模型执行。"** 明确 guard 无感知机制。
- §4.2 末尾：**"用户若确需临时直跑，由用户侧改 config 或在对话中显式授权，guard 不读模型可写的标记。"**

"在对话中显式授权"若 guard 不读标记，那这句话**不可实现**——用户说"允许"跟没说一样，除非用户改 config。而 §3.6-4 自己已经承认这一点。两处必须对齐。

**建议**：§4.2 删去"或在对话中显式授权"，只保留"用户本人修改 config（`enabled:false` 或临时关闭对应规则）后执行"。若要保留"对话授权"的语义，必须给出**用户侧写入、模型不可写的标记通道**（如 host 层 UI 按钮 / 独立的用户态文件），并说明 guard 如何读取它——当前设计没有这一层，不要留下"看似可行实则无效"的表述。

### 3. "非 skip 段"表述含混，可能诱导实现者把 cat 段对 §3.4 也跳过（v4 新表述带来的歧义）

两处：

- §3.6-1："每个**非 skip 执行段**独立跑'每一条规则'"
- §3.4："对 §3.6 切出的每个**非 skip 段**取 argv"

问题：§3.6 定义了两份 skip 列表，但没有统一定义"skip 段"指哪个。若实现者理解为"不在 buildLintNonExecHeads 里"→`cat .sessions/bill.json` 的 cat 段会被跳过 → §3.4 **漏拦**（正是 v4 要修的 🔴1 重新出现）；若理解为"不在任何列表里"→`echo cost_bill.py` 会进入 §3.4 → 又回到问题 1 的误拦。

**建议**：删除"非 skip 段"这一术语，改为显式表述：

> "对每个段，每条规则**各自**做首 token 判定：§3.1 用 buildLintNonExecHeads 跳过；§3.4 用'buildLintNonExecHeads 且不在 dataReadHeads'跳过。不存在跨规则统一的 skip 段概念。"

## 🟡 建议级

### 4. §3.3b"按保守拦处理（不做 size 放行）"表述含混

"不做 size 放行"到底指：① 相对路径跳过 3.3b（只靠 3.3a），还是 ② 相对路径无 range 一律拦（不论大小）？两种读法行为差异很大（100 行小文件 vs 3000 行大文件）。read 通常传绝对路径，实际影响小，但文档应写成可执行判定：

> 相对路径：3.3b 不适用（不取 size），3.3a 仍适用；statSync 异常同理跳过 3.3b。绝对路径：statSync 取 size 按阈值判定。

### 5. §7.5 config 写权限的缓解方案过于笼统

"另设用户侧控制（如 host 层只读挂载 config）"只是方向，不可执行。建议补具体落点：host 层将 `cordis.patch.yml` 所在目录设为只读（Windows ACL / 只读挂载），或把 `enabled` 之外的关键规则**硬编码进插件**（不可配置），使模型即便改 config 也关不掉核心拦截。这一条优先级最高（文档自己也说了），应在 §7.5 给出至少一个可执行方案。

### 6. 外壳包装"静默放行"建议加可观测 counter

§3.6-5 说"静默放行"，§6 列为已知边界。建议加 `counters.shellWrapped++`（识别到首 token ∈ {`&`, `Start-Process`, `cmd`, `bash`, `pwsh`, `.\*.ps1`} 等外壳时计数），不拦但可观测——否则用户永远不知道有多少 build 走外壳绕过了，"硬强制"的实际覆盖率不可知。

### 7. §3.1 eslint "能从 exec 工作目录可靠解析"中"exec 工作目录"来源未说明

建议在 §7 仍需实测清单加一项："确认 exec 上下文是否提供工作目录（如 `exec.cwd` / `exec.agent.session.header.cwd`），否则相对路径一律按保守拦处理"。这一项决定了 eslint/tsc 单文件放行的可用性。

### 8. §9 引用编号可再核对

§9 写"§7 第 7/10/11/12 项"——§7 仍需实测列表实际编号为 4~12，第 7 项是"误伤正反例"、第 10 项"skip/§3.4 交叉"、第 11 项"statSync 基准"、第 12 项"外壳包装"。四者合起来覆盖了"误伤·交叉·基准·边界"，但"绕过"一词更对应第 12 项。属措辞微差，不影响执行。
