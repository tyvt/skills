## 需要警惕的问题

1. **墙钟、tool、LLM、TTFT 可能重叠，不能简单相加。**
   orchestrate 是工具耗时，是否内部还包含子代理 LLM？如果包含，就不能既算 tool 又算 LLM 浪费。报告说 orchestrate 215min 占总墙钟 26%，但 tool 列里已经含它；TTFT 又在 llm 里。直接说“三大根因合计”会重复归因。应先画每会话关键路径：`wall = 串行 LLM + 串行 tool + 用户等待 + idle`，只把关键路径上的段算根因。

2. **总量最大 ≠ 每个长会话的主因。**
   dd6e0d52 的主因是 220 步 × TTFT，不是 orchestrate；ec65ff86 是 ask_user 长尾。建议按会话聚类：orchestrate 型、ask_user 型、TTFT/步数型、job_output 型，分别给规则。

3. **ask_user 的“80 次/85 分钟”被长尾主导。**
   ec65ff86 三次 20min、dde42845 四次 18.4min，两个会话就占约 45%。所以不是“频繁弹问题”单一主因，而是少数超长等待。压到 20 次以内缺证据；应先分必要澄清/可推断/审批/选项，并处理长等待：提醒、默认选项、异步、超时默认。

4. **job_output 阻塞等待不等于浪费。**
   如果后台任务本身要跑 12min，心跳监听不会减少任务运行时间，只改善可观测性/可取消性/并行度。报告说“替代长阻塞等待”逻辑上要改成：后台任务 + 事件通知 + 超时取消 + 等待期间并行做别的；否则省不了那 54min。

5. **建议的量化偏乐观。**
   “orchestrate 今日可省 60–80 分钟”需要拆成：超时重试浪费、失败重试、短任务误用 full 的可节省。平均 96s/次不能直接推“都该直跑”，因为 orchestrate 可能确实完成了多步工作。90s 软上限也可能造成拆解/重试成本，需按 op 和任务类型设阈值。

6. **步数收口要防副作用。**
   “>120 步强制收尾/换会话”可能丢上下文、增加重复整读和交接成本。更稳的是：>120 步触发评估，检查无效步（重复读、工具错误、无进展循环），窗口 60% 提醒收尾，而不是硬切。

修正版一句话结论可以写成：

> 今日墙钟主要被少数长会话拉长；按关键路径，orchestrate 超时/重试和 ask_user 长尾是最明确的浪费，百步级 TTFT 是结构性放大器；但需扣除 orchestrate 的真实计算和必要用户等待，不能把所有耗时都归为可优化。

## 落地建议优先级

1. **先做“可节省时间审计”**：超时次数×超时上限、超时后重试、失败 orchestrate、ask_user 中位数/P90、无效步数、重复整读实际耗时。再定规则。
2. **orchestrate 分级路由**：短命令/单文件/小改动默认直跑；`full` 只给多模型分解任务；按 op 设 90–180s 软上限，超时拆小而非盲目重试。
3. **ask_user 合并 + 长等待治理**：一次问多个待定项、给默认选项；长等待提醒/异步，不追求单纯压次数。
4. **步数治理治无效步**：重复整读缓存/摘要、先 grep 后 offset/limit、工具错误预检和一次重试；>120 步提醒评估，不硬切。
5. **job_output 改后台事件驱动**：心跳监听可以保留，但要明确它不减少任务运行时间；真正收益来自并行、提前失败、取消和超时。
6. **做一周 A/B**：短任务直跑 vs orchestrate，比较墙钟、成功率、返工率；否则“禁止滥用”容易变成拍脑袋。

一句话：**分析值得作为诊断起点，但要把“总量归因”升级为“关键路径归因 + 可节省估算”，并按会话分型落规则。**
