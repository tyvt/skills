### 一、为什么“回退靠 git”可以合法地砍掉大段内容？

你提到“回退什么的，都有 git”。这是对的。对于 DSH 内部的代码变更，回滚本来就不该在计划里长篇大论。
*   以前写：“风险：如果改错，需要执行 `git checkout -- api.py`，然后清理 `__pycache__`，再回退配置……”
*   现在直接写：“风险：**无**。变更在独立分支，回退 `git revert`。”
*   审核员看到“git revert”，就知道你有安全网，完全不会揪着这点不放。

同理，大段粘贴的**“现状与证据”**（比如把 100 行源码贴进计划）和**“冗长的背景科普”**，在审核时其实就是噪音。Grok 需要的是：**你打算改什么、改动逻辑对不对、怎么验证。**

### 二、给主控和 Grok 立规则（无需改代码逻辑）

我们要解决的是“计划太啰嗦”，但产出计划的是主控模型（`planner`），审核计划的是 `plan_review`。要让这步生效，只需在两端的 Prompt 里加约束：

#### 1. 强约束主控模型（改 `PLANNER_SYSTEM`）
主控在生成计划文件时，必须遵循**极简骨架**：
```text
在生成 .plan/*.md 时，必须严格使用以下 4 段式，禁止扩写：
1. 前因后果（≤3 句话，说清痛点）
2. 现状与证据（只写行号/字段名，**严禁**大段贴源码）
3. 实施方案（逐步写清改哪里，不写具体代码实现）
4. 验证计划（只写怎么跑测试）
【硬性禁令】：
- 严禁写「风险与回滚」章节。如果非要写，只写一行：“变更受 git 管理，直接 revert”。
- 严禁把完整的 JSON/YAML 配置贴进计划，只写 diff。
```

#### 2. 强约束 Reviewer（改 `_PLAN_REVIEW_SYSTEM`）
Grok 不需要看“背景科普”，也不需要看“回退预案”。
```text
请在审核时，只关注以下核心要素，忽略非核心的格式与背景：
- 方案是否遗漏了必要文件或依赖？
- 边界条件（如空值、并发、异常捕获）是否处理？
- 验证计划是否覆盖了改动的风险点？
如果计划明确标注了“变更受 git 管理”，则**不要求**计划编写冗长的回滚步骤。
```

### 三、如果一定要在传输层做“有损裁剪”，切哪里？

既然你已经确认了要“砍掉冗长证据”，那么 `api.py` 可以做一个**有损的结构化抽取**，只把最核心的段落送给 Grok。

在不改变原计划文件的前提下，在送审时做切割：
**只提取 `## 实施方案` 和 `## 验证计划` 两节，外加 `## 前因后果` 的第一段。**

**有损裁剪的底线**：**绝对不能剪掉** `实施方案` 里的具体步骤，也绝对不能剪掉 `验证计划`。如果 grok 看不到你要怎么改，它就会开始瞎猜；如果看不到你怎么验证，它就会报一堆“缺少测试”。

**代码实现建议**：
废弃复杂的 `_condense_plan` 状态机，写一个简单的按 `##` 标题切分的函数：
```python
def _extract_core_for_review(plan_text):
    sections = split_by_h2(plan_text) # 按 ## 标题切分
    keep_keywords = ["前因后果", "实施方案", "验证计划", "设计", "方案"]
    core = []
    for title, content in sections:
        if any(kw in title for kw in keep_keywords):
            # 如果是「前因后果」，最多截取前 500 字，防止它写论文
            if "前因后果" in title and len(content) > 500:
                content = content[:500] + "\n... (前置背景已截断)"
            core.append(f"## {title}\n{content}")

    # 如果截取后为空，为了安全，退化为送原计划
    if not core:
        return plan_text
    return "\n".join(core)
```
这样，哪怕原计划有 15k 字，其中 10k 是冗长的源码贴图和回滚推演，切完只剩 `实施方案` 和 `验证计划` 的 3-4k 字。**Grok 的审核耗时将立减 60%，且因去除了背景噪音，审核注意力反而更集中。**
