# 2026-11-13 (Friday) ChatLog:
**user [peer=github.com-tyvt-skills]**: 本次会话 P0 级优化点评估
先给结论：108.3k 未命中里约 65–70% 是本可避免的，集中在 4 个动作上；编排器 9 次调用中 4 次零产出（grep 1 次、build 2 次、plan_review 部分），有效利用率约 50%。以下按浪费量排序。

P0-1 编排器接管本地窄检索，首次调用即烧 18k 未命中
证据：step 1 orchestrate {op:"full"} 让编排器去 grep 三个关键词，返回的是「我无法访问你本机 D 盘」+ 三套命令模板（planner 665+1574 token），宿主单步输入 18,451、未命中 18k。step 2 改用内置 grep 一次命中 17 处，只花 1,227 token。

根因：orchestrate op:"full" 的 planner 链路没有接入宿主 grep/read 能力，对「本地检索」这类确定性任务它只能输出建议文本；而 AGENTS.md 的触发词表（"检索"）反而把这类请求引向了编排器。

改法：

规则层把「单目录 + 关键词已知的 grep」划为直跑豁免，与「单文件窄 read」同级，不等 gate；

编排器侧给 planner 加一条硬约束：任务含明确本地路径时，直接 generate_command 调 rg -n，禁止输出「我无法访问磁盘」类模板；

对编排器返回"无实际执行"的响应做熔断标记，同一会话内不再把同类请求投给 op:"full"。

P0-2 483 行组件整读两遍，改的却是 L379–430 的 3 行
证据：step 3 read 1–400 行（单步输入 26,613，未命中 6,298），step 4 再读 400–483。实际改动只有 .kd__boxes--company 和 .kd__boxes--stack 两条规则。整个文件 146 行 script + 253 行 style，本次任务对 script 零依赖。

根因：定位阶段没有先用 grep -n "kd__boxes--" 拿行号，直接整读。cost-meter 的 18k 告警也发生在这一步之前、没有触发改道。

改法：

样式类改动默认路径固定为：grep 类名 → read offset/limit ±30 行；

把「单文件 >300 行且任务只需局部行」的整读列为 gate 拦截项，提示改用 offset/limit；

cost-meter 在单步未命中 >10k 后应强制下一步只能窄读（见 P0-6）。

P0-3 build 基线 stall 后同形态重试两次，最终判定根本不需要跑
证据：step 8、step 13 各执行一次 orchestrate full 跑 npm run build，两次都 120s stall（累计 240s + 编排器 2 次调用 ~1.6k token）。step 25 最终结论是「本次仅 CSS 增量，提交钩子 lint 通过即可」——也就是说第一次 stall 后就该直接下这个判定。这正好踩了 AGENTS.md 明文：「orchestrate 返回 stalled 必须查 .task-state 与 stderr 尾部，而不是重试同一形态」。

根因：build-gate 只要求"见基线"没给豁免路径，模型为了满足 gate 硬跑；stall 后又按"再试一次"直觉重试。

改法：

给 build-gate 增加豁免白名单：改动仅含 scoped CSS / 注释 / 文案时，hook 直接放行并记录"CSS-only，build 豁免"；

同一会话内 orchestrate 对同一命令 stall 一次后打标记，第二次调用前强制要求换形态（如查 .task-state/*.state.json）或直接放弃并写明"未执行 + 原因"；

stall 的 stderr 尾部应该由编排器自己解析成一句话（本次尾部只有 LangChain 弃用警告，信息量为零）。

P0-4 计划确认与提交方式分两次 ask，违反"一次问清"硬规则
证据：step 10 问「是否确认实施」，step 14 再问「如何处理 Git 提交」。AGENTS.md 写得很明确：「计划确认轮必须把可预见待定项（提交方式/推送/是否重建）一次问清（hook 拦截二次 ask）」。实际 hook 没有拦住。

根因：hook 只按"同轮二次 ask"计数，跨轮（step 10 → step 14）不触发；而提交方式的询问天然发生在改动完成之后。

改法：

把 hook 的判定窗口从「同一 step」扩到「同一 turn」，改动类任务首个 ask 未覆盖"提交方式"时直接拦截并给出合并模板；

或者更简单：ask_user_question 在含 edit/write 的 turn 里，若问题数 <2 且未含提交选项，warning 级提示（不阻断）。

P0-5 长命令输出全量回灌：rebase 2909 行 diff 统计、status 一堆无关目录
证据：

step 18 git pull --rebase 输出 22 个文件、2909 insertions(+), 68 deletions(-) 全进上下文，单步输入 1,444；

step 21 父仓 git status --short 把 .tmp-bug6409/、.tmp-bug6478/、22438、22441、22503、worktrees/ 等无关未跟踪目录全打出来。

根因：直接裸跑 git 命令，没有用 -q、没有限定路径、没有截尾。

改法：

rebase/pull 统一加 -q，或管道 | Select-Object -Last 15；

父仓状态查询限定 git status --short zhi2-web-admin；

在 submodule-commit skill 里把这些命令模板固化（该 skill 已有 git-ab.mjs 封装，把 status/pull 也封进去即可）。

P0-6 cost-meter 只告警不刹车，阈值形同虚设
证据：step 2 收到「上一步未命中 18k，极高」的告警后，模型继续整读文件（step 3 又 6k 未命中）；step 16–17 收到「连续 2 步 >10k」后，也只是照常推进。告警文本每次都一样，模型已经脱敏。

根因：cost-meter 是 observer，没有 enforcement 能力。

改法：

未命中连续 2 步 >10k 后，由 hook 而非提示词限制下一步的工具白名单为 {read with offset, grep with path+include}，其余调用直接返回「cost gate: 请先用窄读」；

会话等效成本 >150k 时，对 orchestrate op:"full" 直接拒绝，只允许直跑窄命令。
