## 🔴 阻塞级（落地前必须解决）

### 1. "带 include 的根级 grep 放行"存在逻辑漏洞

§3.2 规定"带 include 放行"，但 include 缩窄的是**文件类型**而非**目录范围**。`grep -r "foo" --include="*.ts" .` 依然全仓扫描，照样打穿 prefix cache——这正是规则想防的场景。

- **建议**：include 放行必须**同时**要求 path 非仓库根；或改为"path 必须指向具体模块目录"作为唯一放行条件，include 仅作辅助。
- 另外"具体模块目录"需要可操作的判定标准（如 path 深度 ≥2、或命中配置的模块白名单），否则实现时会含糊。

### 2. "账单直查"规则与子 ctx 假设自相矛盾

§3.4 写"命令行含 cost_bill.py 或 .sessions **且非经 orchestrate**"，但 §3.5/§7.2 说编排器内部子 ctx 有独立 layer、guard 默认不覆盖。若子 ctx 确实不触发 guard，则走到本 guard 的 pwsh **天然就是宿主直跑**，"非经 orchestrate"条件恒真、无需判断；若子 ctx 会触发，则必须靠 `delegationDepth>0` 放行，而这个判断恰恰是最大风险点。

- **建议**：删除"且非经 orchestrate"表述，改为"凡进入本 guard 的 pwsh 命中即拦"；把"子 ctx 是否触发"作为 §7.2 实测项统一处理，不要在两条规则里给出互相矛盾的假设。

### 3. 部分规则无法用纯正则实现，复杂度被低估

- **eslint 规则**："仅当目标为目录/通配/仓库根"——正则无法判断 eslint 的位置参数是文件还是目录，需要解析 argv。
- **vue-tsc/tsc 白名单**：`(?!--noEmit\s+-p\s+\S+)` 这种负向前瞻只对**紧跟位置**生效；`vue-tsc --project x --noEmit` 或 `tsc --noEmit -p tsconfig` 都会绕过白名单。而 §3.1 对 vue-tsc 放行、对 tsc 拦截的不对称（`tsc -p tsconfig` 拦、`vue-tsc --noEmit -p` 放）也缺乏理由——两者 `-p` 都可能是项目级或单文件级配置。
- **建议**：明确这些规则需要**轻量 argv 解析**而非单条正则；统一 tsc/vue-tsc 的判定口径（按 `-p` 指向的 tsconfig 是否覆盖单文件来放行，而非按工具名区分）。

## 🟠 重要级（影响可用性/正确性）

### 4. 单调 guard 缺少"单次放行"逃生舱

guard 返回字符串即拒绝、不可强放行。误伤时用户只能：改全局配置（粒度太粗）或把命令缩到单文件（有时做不到，比如必须跑一次 `git commit -m "fix npm run build 报错"` 这种命令行**字符串含关键词**的场景）。

- 文档未提及**命令行字符串内含关键词**的误伤（`echo "npm run build"`、commit message、日志 grep 等），这是正则匹配 command 的固有误伤。
- **建议**：① 在文档 §6 明确列出该误伤场景及缓解（如只在命令**首段**匹配、或排除引号内内容）；② 考虑一个受限逃生舱（如 `enabled:false` 之外的 per-turn 临时开关），并在拒绝文案中提示。

### 5. "重复整读记忆集"的会话隔离未验证

§3.3 说"本会话已完整读过的文件"做记忆集，但 guard 是全局 layer，回调里是否拿得到 `sessionId` 未确认。若拿不到，只能用全局记忆集 → A 会话读过、B 会话再读被误拦（跨会话污染）。

- **建议**：把"exec 是否携带 sessionId/agent 上下文"加入 §7 实测清单，并作为记忆集方案的前置条件；拿不到就退回"纯字节数门禁"单规则。

### 6. 白名单列表混入了规则外的工具

§3.5 标题是"必须白名单防误伤"，但列表里的 `edit/write/mcp_gateway/skill/todo_write` 根本不在 §3 任何拦截规则内，不需要白名单。白名单应只列"可能命中规则但需放行"的窄例外（orchestrate、单文件 eslint、带 `-p` 的 tsc、子 ctx、带 range 的 read/grep）。

- **建议**：区分"规则不匹配（天然放行）"与"命中规则但白名单放行"两类，避免实现时误加白名单分支。

### 7. fail-open 需可观测

§4.1 catch 里 log.warn 后返回 undefined（放行）。对"硬强制"目标，静默 fail-open 会让 bug 隐形。

- **建议**：加异常计数器并在插件 notice 暴露；异常率超阈值时告警，便于发现 guard 崩溃导致的规则失效。

## 🟡 建议级（完善度）

- **§3.1 正则**：`npm run build:prod`、`lint:fix` 会被 `\bbuild\b` 命中（符合预期）；但需确认 `\b` 对 `-`/`:`/空格 的边界行为，建议 selftest 覆盖这些变体。
- **字节阈值**：文档称与 token-guard 一致，建议核对 token-guard 实际值，避免两套门禁口径漂移。
- **§4.1 骨架**：`counters` 未定义、`disposer` 在 guard 注册随 ctx 生命周期自动清理时可能冗余，实现时确认即可。
- **§5 灰度**：先开 `blockRootGrep`+`blockWholeRead` 的顺序合理，但 `blockWholeRead` 依赖记忆集（见问题 5），建议把它排在记忆集验证之后再开。

---

## 落地前补充验证项（在 §7 基础上）

1. `exec` 是否携带 `sessionId` / `agent.delegationDepth`（记忆集与子 ctx 放行都依赖它）。
2. `exec.arguments` 在 pwsh/read/grep 下的真实字段结构（含 command vs script、path 缺省表现）。
3. eslint/tsc 位置参数解析所需的最小 argv 信息是否可得。
4. 命令行字符串含关键词的误伤样本（构造 3~5 条 selftest 反例）。

---

## 结论

**设计方向正确，可以推进，但需先修订 §3.2、§3.4、§3.1 三处规则逻辑，并补上误伤场景与逃生舱说明**。修订后再按 §9 流程建四件套、写 selftest。最大风险仍是问题 2/§7.2 的子 ctx 误拦——建议把它作为第一个实测项，实测结论出来前不要开启 `blockBuildLint`。
