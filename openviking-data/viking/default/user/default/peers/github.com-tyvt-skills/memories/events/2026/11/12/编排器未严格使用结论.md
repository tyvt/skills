## 分析结论：**没有严格使用 langgraph-orchestrator 编排器**

我扫了 DSH 全部 1927 个会话存档（`C:\Users\Administrator\.dsh\sessions\**\session.v4.jsonl.zstd`），聚焦最近 7 天（2026-11-05 ~ 11-12）的 **303 个会话 / 288 个有工具调用**。对照 `dsh-token-policy`（重活——大文件整读 >300 行、全量 lint/build、账单/大结果查询、编码实现——应先走 `orchestrate`）逐条核对，结论是**基本没走编排器**，属于明显不达标。

### 关键数据

**1. 编排器几乎缺席**
- 最近 7 天 `orchestrate` 总调用 **21 次**，且只集中在 11-10（16 次）和 11-11（5 次）两天；11-05 / 11-06 / 11-07 / 11-09 四天 **0 次**。
- 同期 `pwsh` 直跑 **11,174 次**、`read` 4,654 次、`grep` 2,517 次。

**2. 明确该走编排器的重活，绝大多数直接做了**
| 信号 | 应走 orchestrate | 实际 |
|---|---|---|
| 全量 build / lint / vue-tsc / tsc | 应走 | 直跑 **585 次**，分布在 **164 个会话** |
| 其中在"含 orchestrate 的会话"里 | — | 仅 3 次 |
| 其中在"完全没用 orchestrate 的会话"里 | — | **582 次** |
| 无 offset/limit 的整读 read | 应走 | **1,535 次** |

即：build/lint 直跑的 582/585 都发生在完全绕过编排器的会话里。

**3. 反样本：重活最多的都是零编排会话**
- `门户` 项目单会话直跑 build/lint **16 次**，`苏州房地产V3` 系列单会话 12/12/12/10/9 次——全部 `orch=False`。
- `苏住房防汛C端` 反复手跑 `npx vue-tsc --noEmit`，也没走编排器。

**4. 21 次 orchestrate 里还有"用错"的**
- 多次是 `op=list`（仅列举工具/模型池），不是真正执行重活；
- 有些是 `op=tool` 把单条窄命令丢给编排器——这跟 policy"单条窄命令可直接执行"的判断标准也没对齐，属于把编排器当壳子用。

### 结论
- **不算"严格使用"**：编排器是"偶尔用、局部用"，日常重活（build/lint/整读/检索）基本是宿主直接开 pwsh/read/grep 硬刚。
- **最该走没走的类别**：build/lint 验证（585 次里 582 次绕过）和整读（1535 次无 range），正是 token-policy 点名要求走 `orchestrate` 的两类，也是 token 成本最容易失控的地方。
- 只有 11-10 那批禅道 bug 修复（苏住房G 等）真正按 `op=tool`/`op=full` 走了编排器，是少数合规样本。
